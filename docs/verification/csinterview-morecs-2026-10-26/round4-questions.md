질문 댓글의 숨은 식별자를 읽어 해설 공개 범위를 정하는 서비스가 있습니다. 사용자는 봇 댓글의 본문과 식별자를 자신의 댓글에 그대로 복사할 수 있지만, 플랫폼이 제공하는 작성자 정보는 바꿀 수 없다고 가정하겠습니다. 복사한 댓글이 공개 범위의 근거로 사용되지 않게 하려면 어떤 검증이 필요한가요?

- A. 숨은 식별자가 지정된 정규식과 일치하는지 검증합니다.
- B. 식별자가 가리키는 질문이 서버에 저장되어 있는지 검증합니다.
- C. 플랫폼의 작성자 정보나 서버의 발행 기록으로 댓글의 출처를 검증합니다.
- D. 댓글 본문의 해시가 봇이 발행한 본문의 해시와 같은지 검증합니다.

해설: 신뢰 경계(trust boundary)는 신뢰 수준이 다른 데이터 사이의 경계이며, 출처 인증은 데이터가 신뢰하는 주체에서 왔는지 확인하는 것입니다. 이번 변경은 봇 소유 댓글이나 발행 이력으로 확인한 댓글만 범위 판정에 전달하는데, 복사 가능한 본문이나 식별자만으로는 발행 주체를 인증할 수 없기 때문입니다.

- A 해설: 정규식 검사는 형식 검증입니다. 공격자가 올바른 형식을 복사할 수 있으므로 댓글의 출처를 증명하지 못합니다.
- B 해설: 저장된 질문인지 확인하면 존재하지 않는 참조를 거를 수 있지만, 그 질문을 참조한 댓글이 봇의 발행물인지는 알 수 없습니다.
- C 해설: 가정상 사용자가 위조할 수 없는 플랫폼 작성자 정보나 신뢰하는 서버의 발행 기록을 사용하면, 복사한 사용자 댓글과 실제 발행물을 구별할 수 있습니다.
- D 해설: 동일한 본문을 복사하면 해시도 동일합니다. 비밀키나 서명 없이 계산한 본문 해시의 일치는 내용의 동일성을 확인할 뿐 작성자를 인증하지 않습니다.

#### 이전 면접2 · basic · 정답 A · src/question-thread.ts:15

댓글 수집기가 일반 댓글 API와 토론 API의 결과를 합칩니다. 같은 댓글이 두 API에 중복 등장할 수 있고, 서로 다른 댓글 종류에서는 숫자 ID가 같을 수 있다고 가정하겠습니다. 한 저장소의 같은 PR 안에서 실제 질문 댓글의 개수를 정확히 세려면 어떤 중복 제거 키가 적절한가요? 각 종류 안에서 ID는 유일합니다.

- A. 댓글 종류와 댓글 ID를 결합한 값을 사용합니다.
- B. 댓글 종류를 제외하고 댓글 ID만 사용합니다.
- C. 댓글 본문의 해시를 사용합니다.
- D. 수집에 사용한 API 이름과 댓글 ID를 결합한 값을 사용합니다.

해설: 복합 키(composite key)는 여러 속성을 결합해 대상을 식별하며, 식별자의 유일성이 보장되는 네임스페이스(namespace)를 키에 포함해야 합니다. 이번 변경의 중복 제거는 댓글 종류와 ID로 구성된 키를 사용하므로, 주어진 범위에서는 API 간 중복을 합치면서 종류가 다른 별개 댓글을 구별할 수 있습니다.

- A 해설: 같은 댓글은 어느 API에서 수집해도 같은 종류와 ID를 가지며, 다른 종류의 동일 숫자 ID는 서로 다른 키가 됩니다.
- B 해설: ID가 종류 안에서만 유일하므로, 서로 다른 종류의 댓글을 하나로 합칠 수 있습니다. ID가 전체 종류에서 전역적으로 유일한 경우에는 사용할 수 있습니다.
- C 해설: 본문이 같아도 별도로 발행된 댓글일 수 있습니다. 내용의 동일성과 객체의 동일성을 혼동한 키입니다.
- D 해설: 동일한 댓글이 두 API에 등장하면 API 이름이 달라 서로 다른 키가 됩니다. 수집 경로는 댓글 자체의 식별 정보가 아닙니다.

#### 이전 면접3 · basic · 정답 D · src/question-thread.ts:19

해설 서비스는 답글이 달린 스레드의 질문 묶음만 공개해야 합니다. 출처와 코드 버전이 유효한 서로 다른 질문 묶음 두 개가 한 스레드에서 발견됐으며, 요청에는 선택 정보가 없습니다. 사용자가 어느 묶음을 대상으로 했는지 추정하지 않는 것이 요구사항이라면, 적절한 처리는 무엇인가요?

- A. 스레드에서 가장 최근에 발행된 질문 묶음의 해설을 공개합니다.
- B. 두 질문 묶음에 속한 해설을 합쳐 공개합니다.
- C. 질문 개수가 더 적은 묶음의 해설을 공개합니다.
- D. 공개를 보류하고 대상을 명확히 지정할 수 있는 별도 스레드를 안내합니다.

해설: 안전한 기본값(fail-safe defaults)은 필요한 조건이 확인되지 않았을 때 허용하는 대신 거부하는 원칙이며, 이런 처리를 fail-closed라고 합니다. 이번 변경은 질문 묶음의 출처가 유효하더라도 스레드의 범위가 유일하지 않으면 공개하지 않으며, 이는 대상 확정 가능성과 출처 신뢰성이 별개 조건임을 보여 줍니다.

- A 해설: 최신 발행물이라는 사실은 요청 대상이라는 증거가 아닙니다. 최신 묶음을 선택한다는 별도 계약이 있어야 가능한 정책입니다.
- B 해설: 두 묶음의 출처가 유효하다는 사실만으로 요청 대상이 두 묶음 전체라고 결론낼 수 없습니다. 합집합 공개는 범위를 확대합니다.
- C 해설: 적게 공개하더라도 잘못된 묶음을 선택할 수 있습니다. 공개량 최소화만으로 대상의 정확성이 보장되지는 않습니다.
- D 해설: 대상이 유일하다는 조건을 충족하지 못했으므로 공개를 보류하는 것이 요구사항에 맞습니다. 별도 스레드는 이후 요청의 대상을 명확히 만드는 수단입니다.

#### 이전 면접4 · advanced · 정답 B · src/learning-command.ts:97

작업 큐가 계산된 해설 응답을 저장한 뒤 외부 댓글로 게시합니다. 배포 전에는 전체 질문 해설을, 배포 후에는 요청 스레드의 해설만 공개하도록 정책이 바뀌었습니다. 코드 버전은 같고, 배포 전에 저장된 응답은 파싱 가능하지만 어떤 질문을 대상으로 계산했는지 복원할 수 없습니다. 재개 시 안전한 정책은 무엇인가요?

- A. 응답의 JSON 구조가 새 타입과 호환되면 저장된 본문을 그대로 게시합니다.
- B. 현재 공개 정책에서 계산된 결과인지 확인하고, 확인되지 않는 구버전 결과는 게시하지 않습니다.
- C. 응답이 참조한 코드 버전이 현재와 같으면 저장된 본문을 그대로 게시합니다.
- D. 기존 응답에 새 정책 버전 표시를 추가한 뒤 저장된 본문을 게시합니다.

해설: 의미적 호환성(semantic compatibility)은 데이터를 읽을 수 있는지를 넘어, 그 데이터의 의미와 보장이 현재 계약에 맞는지를 뜻합니다. 이번 변경은 저장된 해설 결과에 처리 방식의 버전을 기록하고 구버전 결과의 재게시를 차단하는데, 코드 버전이나 JSON 구조의 일치만으로는 새 공개 범위 정책을 충족했다고 볼 수 없기 때문입니다.

- A 해설: 파싱 가능성은 구조적 호환성을 나타냅니다. 본문이 새 정책보다 넓은 범위를 포함하는지 판단할 수 없으므로 게시의 안전성을 보장하지 않습니다.
- B 해설: 결과를 계산할 때 적용한 정책까지 검증해야 재사용 가능성을 판단할 수 있습니다. 범위를 복원할 수 없는 구버전 결과는 새 요청으로 대체하는 등의 처리가 필요합니다.
- C 해설: 코드 버전은 질문의 근거가 같은지 판단하는 정보입니다. 응답을 어떤 공개 정책으로 계산했는지는 별도로 검증해야 합니다.
- D 해설: 버전 표시를 덧붙여도 기존 본문의 공개 범위는 바뀌지 않습니다. 검증이나 변환 없이 표시만 갱신하면 실제 보장과 메타데이터가 어긋납니다.

#### 이전 면접5 · advanced · 정답 C · src/render.ts:13

코드 비교에 대한 질문 댓글에 버전 표식을 넣고, 현재 비교와 같은 버전인지 확인하려 합니다. 질문의 유효성은 head·base·start 커밋의 조합에 의존하며, head가 같아도 나머지 커밋이 바뀌면 다른 비교로 취급한다고 가정하겠습니다. 해시 충돌은 무시할 때, 표식 설계에 대한 올바른 판단은 무엇인가요?

- A. head만 해시해도 출력 길이가 충분하면 다른 비교를 구별할 수 있습니다.
- B. head만 해시하되 짧은 만료 시간을 두면 유효 기간 안의 비교 동일성을 보장할 수 있습니다.
- C. 세 커밋을 순서가 명확한 형태로 직렬화해 해시하면 필요한 비교 동일성을 판정할 수 있습니다.
- D. 세 커밋을 정렬한 뒤 해시하면 각 커밋의 역할을 보존하면서 동일성을 판정할 수 있습니다.

해설: 캐시 키(cache key)나 버전 지문은 유효성을 좌우하는 의존성을 구별할 수 있도록 구성해야 하며, 해시는 입력에서 빠진 정보를 복구하지 못합니다. 이번 변경의 질문 버전 표식은 head·base·start의 순서 있는 튜플을 해시한 값을 재사용하므로, 충돌을 무시하는 조건에서 세 커밋의 역할을 포함한 동일성을 확인하지만 작성자의 진위나 이후 변경 방지까지 보장하지는 않습니다.

- A 해설: 입력에서 base와 start를 제외하면 그 값만 다른 두 비교가 같은 해시 입력을 갖습니다. 이는 해시 충돌이 아니라 키에 필요한 의존성을 누락한 문제입니다.
- B 해설: 만료 시간(TTL)은 재사용 기간을 제한하지만, 그 기간 안에 다른 커밋이 바뀌지 않았음을 보장하지 않습니다.
- C 해설: 역할별 순서를 고정한 직렬화는 각 커밋이 어느 위치에 해당하는지 보존합니다. 주어진 의존성과 충돌 가정 아래 비교 버전의 동일성을 판정할 수 있습니다.
- D 해설: 정렬하면 값의 집합은 보존하지만 head·base·start라는 역할은 사라집니다. 같은 커밋 값들이 서로 다른 역할에 배치된 경우를 구별하지 못합니다.
