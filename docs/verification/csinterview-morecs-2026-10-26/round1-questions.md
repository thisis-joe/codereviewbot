- C 해설: 결과의 결정성과 실행의 멱등성을 혼동했습니다. **같은 결과를 생성하는 것**은 그 결과를 계산하는 작업과 자원 소비가 반복되지 않는다는 뜻이 아닙니다.
- D 해설: 서버가 실행했지만 응답만 전달되지 않은 경우와 서버가 실행하지 못한 경우를 클라이언트 관찰만으로 구별할 수 없습니다. 따라서 중복 실행 가능성을 재시도 정책에 반영해야 합니다.

#### 면접3 · basic · 정답 B · src/gms.ts:43

이번 변경은 HTTP 응답의 바이트 청크를 모두 합친 뒤 UTF-8 문자열로 변환합니다. 메모리 사용을 줄이려고 수신 즉시 문자열로 바꾸는 방식을 검토한다고 가정하겠습니다. 전체 응답은 올바른 UTF-8 JSON이지만 한 문자의 바이트가 두 청크로 나뉠 수 있습니다. 전체 바이트를 보관하지 않으면서 원래 문자열을 정확히 복원하려면 어떤 방식이 적절한가요?

- A. 각 청크를 서로 독립적으로 UTF-8 디코딩하고, 얻은 문자열들을 수신 순서대로 이어 붙입니다.
- B. 청크 사이에 미완성 바이트를 유지하는 UTF-8 디코더를 사용하고, 마지막에는 입력 종료를 알립니다.
- C. 각 청크를 독립적으로 UTF-8 디코딩하되, 불완전한 문자 오류를 무시하고 나머지 문자열을 이어 붙입니다.
- D. 항상 청크 두 개를 합쳐 독립적으로 UTF-8 디코딩하고, 다음 두 청크도 같은 방식으로 처리합니다.

해설: 문자 인코딩(character encoding)은 문자를 바이트열로 표현하는 규칙이며, UTF-8에서는 한 문자가 여러 바이트를 차지할 수 있습니다. 전송 청크의 경계는 문자 경계와 무관하므로, 청크마다 독립적으로 디코딩하면 나뉜 문자를 오류나 대체 문자로 처리할 수 있습니다. 상태를 유지하는 스트리밍 디코더는 끝의 미완성 바이트를 다음 입력과 결합하고, 입력 종료 시 남은 바이트의 완결성을 검사해 원래 문자열을 복원합니다. 모든 문자가 단일 바이트이거나 청크가 문자 경계에서만 나뉜다는 보장이 있다면 독립 디코딩도 가능하지만, 문항에는 그런 보장이 없습니다. 이번 변경의 바이트 결합 후 UTF-8 변환은 청크 경계에서 문자가 잘리는 문제를 피하며, 스트리밍으로 바꿀 때도 이 성질을 유지해야 합니다.

- A 해설: 전송 단위와 문자 단위를 혼동했습니다. **청크 경계가 문자 경계라는 보장**이 없으므로 각 청크가 독립적으로 유효한 UTF-8이라고 볼 수 없습니다.
- B 해설: 미완성 바이트를 다음 청크까지 유지하면 청크 경계와 무관하게 문자를 복원할 수 있습니다. 입력 종료 처리는 마지막에 미완성 바이트가 남았는지도 확인하게 합니다.
- C 해설: 오류를 허용하는 것과 원본을 보존하는 것을 혼동했습니다. 불완전한 바이트를 무시하면 **복원에 필요한 정보가 유실**되므로 전체 입력이 올바른 UTF-8이어도 원래 문자열을 되찾지 못할 수 있습니다.
- D 해설: 버퍼 크기 확대와 문자 경계 보장을 혼동했습니다. 두 청크를 합쳐도 **그 묶음의 마지막 경계**에서 문자가 나뉠 수 있으므로 고정 개수의 청크 결합만으로는 충분하지 않습니다.
