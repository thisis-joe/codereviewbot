- D. 재시도도 같은 요청이므로 최초 저장자는 자신이라고 판단하고 재조회 없이 자신의 계산 결과를 사용합니다.

해설: 불확정 결과(ambiguous outcome)는 연산의 실제 반영 여부와 호출자가 관측한 응답이 일치하지 않아 결과를 확정할 수 없는 상태입니다. 원자적 조건부 갱신은 저장 여부를 하나로 결정하지만, 결정된 결과가 호출자에게 전달되는 것까지 보장하지는 않습니다. 재시도의 미갱신은 현재 칸이 비어 있지 않다는 뜻이므로, 자신이 먼저 저장했거나 다른 작업자가 저장했을 가능성을 모두 고려하고 영속 저장된 결과를 사용해야 합니다. 결과 삭제나 덮어쓰기가 허용된다면 재조회한 값이 최초 결과라는 보장도 별도로 필요합니다. 이번 변경의 결과 저장 호출 뒤 게시에 사용할 본문은 영속 결과와 일치해야 하므로, 저장 응답의 실패를 곧바로 미반영으로 해석해서는 안 됩니다.

- A 해설: 현재 시도의 결과를 과거 시도의 결과로 확대 해석했습니다. **재시도의 미갱신은 최초 요청의 실패를 증명하지 않으며**, 자신의 계산 결과가 최초 저장값과 같다는 보장도 없습니다.
- B 해설: 두 가능한 저장 이력 모두에서 현재 영속 결과가 게시의 기준입니다. 최초 저장자를 알아내지 못해도 저장된 결과를 읽으면 최초 결과를 사용하는 목적을 달성할 수 있습니다.
- C 해설: 원자성과 응답 전달 보장을 혼동했습니다. 원자성은 **서버에서 검사와 변경이 나뉘지 않음**을 뜻하며, 응답 유실 시 미반영을 뜻하지 않습니다.
- D 해설: 멱등적 재시도와 최초 실행자의 식별을 혼동했습니다. 같은 조건부 연산을 반복해 덮어쓰기를 피할 수 있어도 **어느 작업자가 먼저 저장했는지는 별개의 정보**입니다.

#### 꼬리9 (↳ 꼬리5) · basic · 정답 A · src/render.ts:150

이번 변경은 명령 댓글에서 만든 식별 표식으로 재개 시 기존 게시를 찾습니다. 식별자의 유일성 조건을 다음과 같이 가정해 주세요. 같은 변경 요청 안에서 댓글 ID는 댓글 종류별로만 유일하며, 일반 댓글과 코드 댓글이 같은 ID를 가질 수 있습니다. 같은 사용자가 두 종류 모두에 명령을 남길 수도 있습니다. 재시도와 별개 명령을 구분할 표식의 근거로 무엇이 적절한가요?

- A. 댓글 종류와 댓글 ID를 경계가 구분되는 한 쌍으로 인코딩하여 사용합니다.
- B. 댓글 ID만 암호학적 해시로 변환하여 충돌 가능성을 낮춘 뒤 사용합니다.
- C. 작성자와 댓글 ID를 경계가 구분되는 한 쌍으로 인코딩하여 사용합니다.
- D. 명령이 속한 스레드의 식별자를 사용하여 그 스레드의 게시를 구분합니다.

해설: 복합 키(composite key)는 여러 속성을 함께 사용하여 대상을 식별하는 키이며, 식별자의 유일성은 그 식별자가 발급된 이름 공간(namespace) 안에서 판단해야 합니다. 댓글 ID가 종류별로만 유일하다면 종류와 ID를 함께 보존해야 서로 다른 댓글을 구별할 수 있습니다. 이 쌍은 같은 댓글의 재시도에서는 유지되고 다른 종류의 동일 ID와는 달라지지만, ID만 해시해도 빠진 종류 정보가 복원되지는 않습니다. ID가 모든 종류에 걸쳐 전역적으로 유일하다면 종류를 포함할 필요는 없고, 여러 변경 요청을 함께 처리한다면 그 범위도 키에 반영해야 합니다. 이번 변경의 질문 묶음 표식에는 댓글 종류와 ID로 만든 명령 키가 전달되어, 재개 시 서로 다른 명령을 잘못 합치지 않는 데 사용됩니다.

- A 해설: 종류가 ID의 이름 공간을 구분하므로 두 값을 함께 사용하면 가정한 범위에서 댓글을 식별할 수 있습니다. 경계를 구분하는 인코딩은 서로 다른 쌍이 같은 문자열로 표현되는 것도 방지합니다.
- B 해설: 해시 충돌과 입력 식별 정보의 누락을 혼동했습니다. 서로 다른 댓글의 ID 값이 같다면 **동일한 입력은 동일한 해시**가 되므로 종류 정보가 없는 문제는 해결되지 않습니다.
- C 해설: 작성자를 이름 공간 구분자로 오인했습니다. 같은 사용자가 두 종류에 같은 ID의 댓글을 남길 수 있으므로 **작성자와 ID의 조합도 유일하지 않습니다**.
- D 해설: 작업의 묶음과 개별 작업의 정체성을 혼동했습니다. 하나의 스레드에 여러 명령이 있을 수 있으므로 **스레드 식별자는 명령 식별자가 아닙니다**.

#### 꼬리10 (↳ 꼬리6) · advanced · 정답 D · src/learning-command.ts:278

이번 게시 작업은 결과를 저장해 재개하며, 작업 저장소는 재시도 예정 시각과 실행 중 상태를 관리합니다. 규모 조건을 바꾸어 다른 작업도 대기한다고 가정해 주세요. 실행 중인 작업은 전체에서 하나만 허용되며, 한 명령의 일시적 실패에는 긴 백오프가 필요합니다. 다른 작업은 그 장애와 무관하게 처리할 수 있습니다. 재시도를 유지하면서 다른 작업의 지연을 줄이는 방식은 무엇인가요?

- A. 실패한 작업의 실행 중 상태를 유지하고 임대를 갱신하면서 백오프가 끝날 때까지 기다립니다.
- B. 실패한 작업의 결과만 영속 저장하고 실행 중 상태는 유지한 채 다른 작업의 조회 주기를 줄입니다.
- C. 실패한 작업의 재시도 예정 시각을 미래로 옮기되 실행 중 상태와 소유자는 그대로 유지합니다.
- D. 실패한 작업을 미래 시각의 대기 상태로 돌리고 실행 슬롯을 반납하여 다른 준비된 작업을 실행합니다.

해설: 선두 지연(head-of-line blocking)은 앞선 작업의 대기가 뒤의 독립적인 작업까지 막는 현상입니다. 실행 슬롯이 하나라면 실패한 작업이 슬롯을 가진 채 백오프하는 동안 다른 작업은 외부 장애와 무관해도 실행될 수 없습니다. 재시도 상태와 예정 시각을 저장하고 슬롯을 반납하면 대기 시간과 실행 자원 점유를 분리할 수 있습니다. 다른 작업의 실행 가능성과 공정한 선택이 전제되며, 모든 작업이 같은 장애에 의존한다면 슬롯을 반납하는 것만으로 성공을 보장하지는 못합니다. 이번 변경의 게시 호출에서 발생한 실패는 작업 저장소의 재시도 경로로 전달되며, 기존 저장소는 소유자를 해제하고 예정 시각을 기록하는 방식으로 실행 슬롯을 다시 사용할 수 있게 합니다.

- A 해설: 임대 유지와 처리량 보장을 혼동했습니다. 임대를 갱신하면 소유권은 유지되지만 **대기 중에도 유일한 실행 슬롯을 점유**하므로 다른 작업이 막힙니다.
- B 해설: 영속성과 스케줄링을 혼동했습니다. 결과 저장은 복구에 도움이 되지만 **저장 자체가 실행 슬롯을 해제하지는 않으며**, 조회 주기를 줄여도 실행 중 상태에 따른 진입 제한은 남습니다.
- C 해설: 실행 가능 시각과 현재 자원 점유를 혼동했습니다. 예정 시각은 다음 실행 시점을 제한하지만 **실행 중 상태가 유지되면 전역 슬롯은 계속 점유**됩니다.
- D 해설: 미래의 재시도 기회는 저장된 상태로 유지하면서 현재 실행 슬롯은 다른 작업에 넘길 수 있습니다. 백오프를 작업의 대기 상태로 표현하여 장애와 무관한 작업의 진행을 허용합니다.
