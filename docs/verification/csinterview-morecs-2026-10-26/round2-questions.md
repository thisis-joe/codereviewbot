- C 해설: 필요한 파일이 없으면 준비 완료 기록만으로 다음 단계를 수행할 수 없습니다. 관련 진행 상태를 함께 초기화하면 준비 단계를 건너뛰지 않고, 남아 있는 원본으로 필요한 데이터를 다시 만들 수 있습니다.
- D 해설: 일시적인 접근 실패와 **영구적인 데이터 소실**을 혼동했습니다. 지수 백오프는 일시 장애나 부하 완화에는 유용하지만, 백업도 없는 삭제 파일은 같은 읽기를 반복해도 복원되지 않습니다.

이번 코드처럼 질문 내용과 보기를 직렬화해 ID를 계산한 뒤 맵을 만든다고 하겠습니다. 규모 분석을 위해 문항 길이 제한은 없다고 가정합니다. M개 질문을 각각 한 번 직렬화·해시하며, 그 입력의 총 바이트 수는 S입니다. 바이트당 처리 비용은 상수이고, 생성된 ID는 고정 길이이며 맵 연산은 평균 O(1)입니다. 이후 고정 길이 ID로 참조 N개를 조회할 때 전체 예상 시간은 무엇인가요?

- A. 고정 길이 ID를 사용하므로 전체 예상 시간은 Θ(M+N)입니다.
- B. 각 참조를 찾을 때 질문 내용을 다시 해시하므로 전체 예상 시간은 Θ(SN+M)입니다.
- C. 질문 내용 처리와 맵 연산을 함께 계산하면 전체 예상 시간은 Θ(S+M+N)입니다.
- D. M개 질문 각각을 처리할 때 전체 S바이트가 필요하므로 전체 예상 시간은 Θ(SM+N)입니다.

해설: 입력 크기 기반 복잡도(input-size complexity)는 항목 개수뿐 아니라 항목을 처리하는 데 필요한 데이터 양도 비용에 반영합니다. 고정 길이 해시 결과를 얻더라도 가변 길이 원문은 읽어야 하므로, 질문 전체의 직렬화와 해시에 Θ(S), 맵 구성과 참조 조회에 예상 Θ(M+N)이 듭니다. 따라서 합계는 예상 Θ(S+M+N)이며, S가 M 이상인 표현에서는 Θ(S+N)으로도 쓸 수 있습니다. 문항 길이가 일정한 상한으로 제한되어 S=O(M)이면 원래의 예상 Θ(M+N) 분석으로 단순화됩니다. 이번 변경의 맵 생성은 questionId를 호출하며, 이 함수는 질문과 보기를 직렬화해 해시하므로 ID 생성 비용과 생성 후 조회 비용을 구분해야 합니다.

- B 해설: 색인 전처리와 참조 조회를 혼동했습니다. 이 조건에서는 **내용 해시는 질문마다 한 번** 수행하고, 조회에는 이미 주어진 고정 길이 ID를 사용합니다.
- C 해설: S바이트를 처리하는 비용과 M번의 삽입 및 N번의 조회 비용을 더하면 됩니다. 해시 계산을 전처리 단계로 옮겨도 그 비용 자체가 사라지는 것은 아닙니다.
- D 해설: 질문 하나의 크기와 모든 질문의 크기 합계를 혼동했습니다. S는 **M개 질문을 합친 총량**이므로 다시 M을 곱하면 같은 처리를 중복 계산합니다.
