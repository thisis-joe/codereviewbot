이번 변경은 해설 본문과 검증 표식을 하나의 저장 결과로 전달합니다. 동시 실행을 허용하는 대안을 가정하겠습니다. 두 워커가 같은 작업의 결과가 비어 있음을 각각 읽고 서로 다른 결과를 만들었습니다. 각 결과 전체를 원자적으로 저장하더라도, 먼저 확정된 결과가 나중 결과로 덮어써지지 않게 하려면 어떤 방법이 적절한가요?

- A. 각 워커가 결과 전체의 쓰기를 별도 트랜잭션으로 커밋하고, 앞서 읽은 빈 상태를 근거로 저장합니다.
- B. DB에서 결과가 비어 있을 때만 저장하는 조건부 갱신을 수행하고, 실패한 워커는 확정된 결과를 읽습니다.
- C. 각 워커가 저장 직전에 검증 표식의 버전이 같은지 확인하고, 같은 버전이면 결과를 교체합니다.
- D. 각 워커 프로세스에 자체 뮤텍스를 두고, 그 프로세스 안에서 한 번에 하나의 결과만 저장합니다.

해설: 경쟁 조건(race condition)은 동시 작업의 실행 순서에 따라 결과가 달라지는 현상이며, 원자적 조건부 갱신은 상태 확인과 변경을 하나의 연산으로 묶습니다. 각각의 쓰기가 원자적이어도 두 워커가 과거에 읽은 빈 상태를 근거로 쓰면 나중 쓰기가 먼저 확정된 결과를 덮을 수 있습니다. DB가 갱신 시점의 빈 상태를 조건으로 평가하면 한 워커만 저장에 성공하고, 다른 워커는 이미 확정된 결과를 사용하게 됩니다. 모든 작성자가 공유하는 잠금으로 확인부터 저장까지 보호하는 방법도 가능하지만, 프로세스별 잠금만으로는 부족합니다. 이번 변경의 saveCommandResult 호출은 본문과 검증 표식을 확정하는 경계이며, 해당 저장 함수는 결과가 비어 있다는 조건을 DB 갱신에 포함합니다.

- A 해설: 원자성(atomicity)과 동시 실행 제어를 혼동했습니다. **각 쓰기가 전부 반영됨**은 보장하더라도, 앞선 조회와 쓰기 사이에 다른 결과가 확정되는 일까지 막지는 않습니다.
- B 해설: 빈 상태 검사와 저장을 같은 원자적 연산으로 수행하므로 두 워커가 모두 저장에 성공할 수 없습니다. 실패한 워커가 기존 결과를 읽으면 처음 확정된 결과를 유지할 수 있습니다.
- C 해설: 검증 방식의 버전과 레코드의 변경 여부를 혼동했습니다. **같은 검증 버전의 서로 다른 결과**가 존재할 수 있으므로 표식 비교는 최초 저장 여부를 판별하지 못합니다.
- D 해설: 상호 배제(mutual exclusion)의 적용 범위를 놓쳤습니다. **서로 다른 프로세스의 자체 잠금**은 상대 워커의 저장을 막지 못하며, 모든 작성자가 같은 잠금을 공유해야 합니다.

#### 꼬리9 (↳ 꼬리5) · advanced · 정답 A · src/question-thread.ts:15

이번 변경은 여러 댓글 목록을 합치고 게시물 식별자로 중복을 제거합니다. 가정상 두 목록을 조회하는 사이에 같은 봇 게시물이 편집되어, 동일 식별자에 서로 다른 질문 묶음이 관측됐습니다. 두 본문 모두 현재 코드 기준의 유효한 질문을 담고 있으며 수정 시각은 없습니다. 목록을 합치는 순서만으로 최신 본문을 선택하자는 대안을 어떻게 판단해야 하나요?

- A. 목록의 결합 순서는 수정 순서를 증명하지 못하므로, 충돌을 감지하면 그 자료만으로 최신 본문을 확정할 수 없습니다.
- B. 나중에 조회한 목록을 뒤에 붙이고 마지막 항목을 남기면, 조회 완료 순서가 수정 순서를 보장합니다.
- C. 같은 게시물 식별자는 같은 질문 범위를 뜻하므로, 어느 본문을 남겨도 해설 대상은 동일합니다.
- D. 두 본문이 모두 현재 코드 기준으로 검증되므로, 질문 참조가 더 많이 포함된 본문을 최신으로 선택할 수 있습니다.

해설: 개체 식별성(entity identity)은 같은 대상을 구분하는 기준이고, 버전 일관성(version consistency)은 그 대상의 어느 상태를 관측했는지를 다루므로 둘은 별개의 문제입니다. 동일 식별자가 서로 다른 본문으로 관측되면 하나의 개체라는 사실은 알 수 있지만, 목록의 결합 순서만으로 수정의 선후 관계까지 알 수는 없습니다. 따라서 주어진 자료만으로 최신 본문을 확정해서는 안 되며, 충돌을 거부하거나 신뢰할 수 있는 버전 근거를 추가로 확보해야 합니다. 두 조회가 같은 스냅숏을 읽거나 원격 읽기에 명확한 최신성 보장이 있다면 판단이 달라질 수 있습니다. 이번 변경의 seen 집합은 동일 게시물의 반복 관측을 제거하지만, 그 자체가 서로 다른 시점의 본문을 일관된 상태로 만드는 장치는 아닙니다.

- A 해설: 관측된 값의 나열 순서와 원본의 변경 순서는 별개입니다. 수정 시각이나 읽기의 최신성 보장이 없으므로 충돌한 본문 중 무엇이 최신인지 확정할 수 없습니다.
- B 해설: 조회 완료 순서와 데이터의 버전 순서를 혼동했습니다. **나중에 완료된 조회가 최신 상태를 반환한다는 보장**이 있어야 이 선택을 정당화할 수 있습니다.
- C 해설: 개체의 동일성과 상태의 동일성을 혼동했습니다. **식별자가 유지되어도 본문은 변경될 수 있으므로**, 같은 게시물이 서로 다른 질문 범위를 나타내는 상태를 거칠 수 있습니다.
- D 해설: 유효성 검증을 버전 순서 판별로 확대했습니다. **현재 코드에 유효함**은 질문 수와 수정 시점 사이의 관계를 보장하지 않습니다.

#### 꼬리10 (↳ 꼬리7) · advanced · 정답 C · src/learning-command.ts:263

이번 변경은 결과가 의존한 코드 버전을 게시 전에 비교합니다. 가정상 불일치하면 결과를 버리고 최신 코드로 다시 생성하도록 바꾸며, 각 생성과 검사는 유한 시간에 끝납니다. 다른 사용자는 제한 없이 코드를 갱신할 수 있습니다. 재시도 횟수를 무제한으로 늘리면 얻는 보장을 가장 정확하게 설명한 것은 무엇인가요?

- A. 각 시도가 유한 시간에 끝나므로, 전체 작업도 유한 시간 안에 버전 검사를 통과합니다.
- B. 충돌할 때 최신 버전으로 이동하므로, 다른 사용자가 계속 갱신해도 재시도마다 완료에 가까워집니다.
- C. 불일치한 결과는 계속 거부할 수 있지만, 검사를 통과할 만큼 코드가 안정되는 구간 없이는 완료를 보장하지 못합니다.
- D. 한 작업의 생성 워커를 하나로 제한하면, 외부 코드 갱신이 계속되어도 버전 충돌로 인한 무한 재시도는 방지됩니다.

해설: 안전성(safety)은 잘못된 일이 일어나지 않는 성질이고, 활성(liveness)은 작업이 결국 진전하거나 완료되는 성질입니다. 낙관적 동시성 제어는 입력이 달라진 결과를 거부할 수 있지만, 경쟁하는 갱신이 반복되면 특정 작업이 계속 재시도하는 기아(starvation)가 발생할 수 있습니다. 각 시도가 끝난다는 사실만으로 무한히 이어질 수 있는 전체 재시도의 종료가 보장되지는 않습니다. 코드가 충분히 오래 안정되고 실행 기회가 주어진다면 검사를 통과할 수 있으며, 재시도 한도는 무한 대기 대신 명시적 실패를 선택하는 대안입니다. 이번 변경의 게시 전 sameRevision 검사는 결과의 전제 불일치를 탐지하는 역할이지 작업의 최종 완료까지 보장하는 장치는 아닙니다.

- A 해설: 개별 연산의 종료와 전체 절차의 종료를 혼동했습니다. **유한 시간의 시도가 무한히 반복될 수 있으므로**, 각 시도의 종료만으로 전체 완료를 증명할 수 없습니다.
- B 해설: 재시도를 단조로운 진전으로 오해했습니다. **비교 대상 자체가 계속 바뀌면** 최신 입력으로 다시 시작해도 완료까지의 거리가 줄어든다는 보장은 없습니다.
- C 해설: 불일치 거부와 최종 완료를 구분한 판단입니다. 외부 갱신이 매번 생성 결과의 전제를 바꿀 수 있으므로 검사 유지와 무제한 재시도만으로 완료를 보장할 수 없습니다.
- D 해설: 생성 워커 사이의 상호 배제와 입력 작성자에 대한 제어를 혼동했습니다. **워커 하나로 제한해도 외부 코드 작성자는 계속 갱신할 수 있으므로**, 충돌 원인이 사라지지 않습니다.

#### 면접4 · advanced · 정답 D · src/question-thread.ts:22

이번 변경은 질문 내용과 코드 기준에서 만든 고정 길이 해시 ID를 Map의 키로 사용해 질문을 조회합니다. 질문 수가 늘어 서로 다른 질문이 같은 해시 ID를 가질 가능성까지 다루려 한다고 가정하겠습니다. '해시 테이블이 충돌을 처리하므로 질문을 잘못 연결할 일은 없다'는 주장에 대한 판단으로 가장 적절한 것은 무엇인가요?

- A. Map이 키를 내부적으로 다시 해싱하므로, 같은 해시 ID를 가진 질문도 서로 다른 항목으로 보존됩니다.
- B. Map의 저장 용량을 늘려 내부 버킷 수를 충분히 확보하면, 같은 해시 ID를 가진 질문도 구별됩니다.
- C. 질문과 코드 기준 전체를 해시 입력에 포함하면, 출력 길이가 고정되어도 서로 다른 입력의 ID는 항상 다릅니다.
- D. Map에 전달된 키 자체가 같으면 원래 질문을 구별하지 못하므로, 충돌 후보를 보존하고 ID만으로 모호하면 선택을 거부해야 합니다.

해설: 해시 충돌(hash collision)은 서로 다른 입력이 같은 해시값으로 변환되는 현상이며, 고정 길이 출력은 임의의 입력 전체에 대해 유일할 수 없습니다. 해시 테이블의 충돌 처리는 서로 다른 키가 같은 내부 위치에 배치되는 문제를 키 비교로 해결하지만, 이미 같은 문자열로 변환된 두 ID의 원래 입력까지 복원하지는 못합니다. 따라서 같은 ID에 여러 질문이 대응할 가능성까지 처리하려면 후보를 보존하고, 추가 구별 근거가 없는 조회는 모호한 것으로 거부해야 합니다. 더 긴 해시는 충돌 확률을 낮추지만 수학적 유일성을 보장하는 것과는 다릅니다. 이번 변경의 available Map은 해시 기반 질문 ID로 해설 대상을 연결하므로, ID의 충돌 가능성과 자료구조 내부의 충돌 처리를 구분해서 이해해야 합니다.

- A 해설: 해시 테이블 내부 충돌과 애플리케이션 식별자 충돌을 혼동했습니다. Map에 **동일한 키 문자열**이 전달되면 내부 재해싱으로 원래 질문의 차이를 알아낼 수 없습니다.
- B 해설: 저장 용량과 식별 정보의 양을 혼동했습니다. 버킷 확장은 내부 배치 충돌을 줄일 수 있지만 **이미 같은 값이 된 키**를 서로 다른 키로 바꾸지는 못합니다.
- C 해설: 입력의 완전성과 출력의 유일성을 혼동했습니다. 모든 관련 입력을 포함해도 **고정 길이 출력의 가능한 값은 유한하므로**, 서로 다른 입력의 충돌 가능성이 없어지지는 않습니다.
- D 해설: 동일 ID의 후보를 보존하면 충돌을 덮어쓰기로 숨기지 않고 감지할 수 있습니다. 요청에 ID 외의 구별 정보가 없다면 임의로 하나를 선택하지 않는 것이 잘못된 연결을 막는 방법입니다.
