## 확인하지 못한 것과 한계

- 최종 라운드의 s1 Q2는 도구 결과의 `call_id` 연결을 묻는 조회·관문 부적합 문항이다. "조회 0" 목표는 충족하지 못했다. 반복 3회를 모두 써서 더 고치지 않았다.
- Q1/Q2만 보면 r3·r4의 이해 필요 평균이 3.63으로 4보다 낮다. 질문이나 코드 주석이 답을 거의 알려 주는 경우가 남아 있다.
- 채점 프롬프트는 r1·r2, `@hey` 프롬프트는 r1에서만 실제 모델로 검증했다. 이후 반복에서는 두 프롬프트가 바뀌지 않았다. `@hey` 근거 상한 변경(`8a5733c`)은 모델로 다시 실행하지 않았다.
- `@hey` 스키마 위반 1건의 원인은 원문을 확보하지 못해 확인하지 못했다(근거 9개 이상으로 추정).
- 채점 스키마 위반 3건의 원인은 피드백이 3문장 상한을 넘은 것으로 추정했다. 통과한 피드백이 대부분 정확히 3문장이었다는 점이 근거다. r1의 실패 프롬프트를 한 번 다시 실행했지만 이번에는 유효한 출력이 나와 원인을 직접 확인하지 못했다. 피드백 상한을 4문장으로 바꾼 뒤 r2의 채점 12회는 모두 첫 시도에 통과했다.
- 표본은 한 저장소의 4개 변경이고, 라운드마다 표본당 1회 실행이다. 같은 이전 묶음의 점수도 채점자에 따라 3.83~4.05로 흔들린다.
- 시나리오 답변은 작성자가 썼다. 실제 개발자의 다양한 답변은 다루지 않았다.
- Codex·Claude 제공자의 실제 출력은 확인하지 않았다. 운영 배포는 하지 않았다.
- r4 s3 채점자는 2문항 묶음에 "사유가 없다"고 적었다. 이는 채점 묶음을 만들 때 사유를 빼먹은 탓이고, 실제 댓글에는 사유가 있다(r3·r4의 5개 미만 묶음 모두 확인).
- r3 s3 심화2는 `fee3cb6` 시점의 `enqueue` 병합이 `recoveryAttempt`를 버린다는 점을 짚었고, 채점자가 코드로 확인했다. 현재 `store.ts`는 같은 head의 병합에서 `recoveryAttempt`를 유지한다.
