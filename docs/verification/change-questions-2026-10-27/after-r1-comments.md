##### 해설

기존 Codex 경로는 실행 프로세스에 시간 제한을 전달했고, 새 직접 호출 경로는 공유 AbortSignal로 HTTP 대화를 제한합니다\. 그러나 <b>로컬 저장소 읽기의 즉시 취소까지 보장하지는 않으며</b>, runner의 busy 해제도 모델 실행이 끝난 뒤이므로 이를 전체 점유 시간의 엄격한 상한으로 해석하면 용량 판단이 잘못됩니다\.

##### 보기별 해설

- **A.** HTTP 왕복은 남은 공통 예산에 묶이지만 로컬 읽기는 즉시 취소되지 않으므로 전체 실행의 종료 상한으로 볼 수 없습니다\.

  > HTTP 요청에는 공유 signal이 전달되지만 저장소 읽기에는 전달되지 않습니다\. 읽기가 끝나지 않으면 실행도 아직 정리되지 않아 runner의 finally에 있는 busy 해제에 도달하지 못합니다\.

- **B.** 공통 신호가 만료되면 기다리는 로컬 파일 읽기도 자동으로 중단되므로 전체 실행의 종료 상한으로 볼 수 있습니다\.

  > AbortSignal 생성만으로 모든 비동기 작업이 취소된다고 오해한 보기입니다\. 저장소 읽기는 해당 신호를 받거나 확인하지 않습니다\.

- **C.** 각 HTTP 왕복이 새 시간 예산을 받으므로 전체 점유 시간은 왕복마다 timeoutMs만큼 늘어납니다\.

  > 시간 제한을 왕복별로 갱신한다고 잘못 읽은 보기입니다\. 신호는 대화 루프 밖에서 한 번 생성되어 모든 fetch에 공유됩니다\.

- **D.** runner의 busy 상태는 시간 제한 신호가 만료되는 즉시 해제되므로 로컬 읽기 지연은 다음 요청에 영향을 주지 않습니다\.

  > busy 해제를 신호 이벤트에 연결한 것으로 오해한 보기입니다\. 실제 해제 지점은 요청 처리의 finally이며 모델 실행이 정리될 때까지 기다립니다\.

### s1 · hey-design.md

API에 보내는 JSON 스키마는 출력 형식을 유도하는 역할이고, 로컬 검증은 반환값이 애플리케이션의 실제 계약을 만족하는지 확인하는 최종 관문입니다\. GMS 요청은 \`strict: false\`이며 JSON 스키마 변환에도 \`unrepresentable: 'any'\`를 사용하므로, 원래 Zod 스키마의 검증 조건까지 API가 보장한다고 볼 수 없습니다\.

##### 이유

변경 전에는 실패 결과가 있는 review만 체크포인트를 비웠기 때문에, 결과 없이 실패한 작업에는 오래된 파일 참조가 남을 수 있었습니다\. DB의 단계 기록만으로 실제 파일의 존재가 보장되지는 않으며, generate·validate는 그 참조로 파일을 읽습니다\. 이번 변경은 준비 단계를 다시 수행하는 비용을 치르는 대신, 결과 없는 실패 작업이 사라진 입력 파일에 의존해 재개되는 위험을 막습니다\.

##### 보기별 해설

- **A.** 복구 예산은 PR 전체의 누적 한도이므로 새 리비전에서도 생성을 막아야 하기 때문입니다\.

  > 선행 실패 작업에서 이어지는 복구 제한을 PR 전체의 누적 한도로 읽은 보기입니다\. 기존 보고서와 리비전이 다르면 실패 전용 분기를 건너뛰어 새 리비전 등록을 판단합니다\.

- **B.** 등록 이벤트에는 headSha만 있으므로 baseSha 변경은 질문 생성에 반영할 수 없기 때문입니다\.

  > 이벤트의 headSha를 전체 리비전 판정과 혼동한 보기입니다\. 컨트롤러는 baseSha와 startSha 변경도 등록 조건으로 검사하고, 실제 실행에서는 플랫폼에서 스냅샷을 다시 얻습니다\.

- **C.** 이전 리비전의 복구 제한이 새 리비전의 정상 생성까지 막는 경로가 될 수 있기 때문입니다\.

  > 실패 전용 분기는 복구 이벤트가 없어도 continue로 끝납니다\. 따라서 리비전 일치 검사를 제거하면 새 리비전에 일치하는 실패 작업이 없어 복구 이벤트가 나오지 않는 경우에도 기존 등록 경로에 도달하지 못합니다\.

- **D.** 새 리비전은 먼저 이전 실패 보고서를 정상 상태로 바꾸어야만 등록할 수 있기 때문입니다\.

  > 이전 실패 보고서의 상태 변경이 새 등록의 선행 조건이라고 읽은 보기입니다\. 기존 등록 조건은 스냅샷 차이를 직접 확인하므로, 이전 보고서를 정상 상태로 바꾸지 않고도 새 리비전을 등록할 수 있습니다\.

### s3 · hey-design.md

같은 실패 작업의 다음 복구 시도에는 같은 deliveryId를 부여해, 여러 컨트롤러가 동시에 복구하더라도 중복 등록을 막기 위해서입니다\. 반면 복구 작업이 다시 실패하면 그 작업의 id와 증가한 복구 차수로 새 키를 만들어, 같은 리비전에서도 다음 재시도를 허용합니다\.

##### 이유

기존 복구 키는 리비전 SHA 조합에 고정되어 있어, 한 번 등록된 키로는 같은 리비전의 후속 복구를 등록할 수 없었습니다\. 새 키는 ‘선행 실패 작업과 복구 차수’를 멱등성 단위로 삼으며, enqueue가 deliveries의 기본 키 제약과 ON CONFLICT DO NOTHING으로 같은 키를 한 번만 받아들입니다\. 활성 작업 사전 조회만으로는 동시 조회 경쟁을 막을 수 없으므로 실제 중복 방지는 이 DB 등록 단계가 담당합니다\. 다음 복구에는 새 키를 허용하되, recoveryAttempt가 3을 넘으면 이벤트를 만들지 않아 무제한 재시도를 막습니다\.

### s4 · hey-wrongPremise.md

**전제와 다른 점**: 반대입니다\. 이번 변경은 번호로 해설을 선택하는 기능을 없애고, 답글을 남긴 질문 댓글로 공개 범위를 정합니다\.

번호를 붙이면 맞는 번호든 틀린 번호든 유효한 해설 요청으로 인식되지 않아, ‘명령을 확인하세요\.’와 도움말 안내가 반환됩니다\. 번호 없이 질문 댓글에 답글로 요청해야 하며, 그 댓글에 포함된 질문들의 정답·해설만 공개됩니다\. 따라서 여러 심화 질문이 담긴 댓글이라면 그 묶음 전체가 대상입니다\.

##### 이유

변경 전에는 인자에서 질문 번호를 추출했지만, 이제는 인자가 없어야 해설 요청으로 처리합니다\. 공개 범위는 신뢰된 게시 댓글의 질문 표식과 저장된 질문을 대조해 결정하므로, 번호로 다른 질문을 선택하는 대신 요청한 스레드에 범위를 묶습니다\.
