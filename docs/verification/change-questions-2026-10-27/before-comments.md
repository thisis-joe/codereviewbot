##### 해설

##### 해설

누적 통신 복잡도\(cumulative communication complexity\)는 여러 요청에서 전송한 데이터 크기의 총합이며, 메모리에 보유한 최종 이력 크기와 구별됩니다\. 이 코드는 모델 출력과 도구 결과를 input에 추가하고 매 요청마다 전체 input을 직렬화하므로, 초기 요청 크기를 P, 라운드당 추가 이력 크기를 d, 요청 수를 R이라 하면 누적 요청량은 대략 RP \+ dR\(R−1\)/2가 되어 C가 맞습니다\. 최대 64라운드와 이력 크기 제한은 실행 범위를 제한하지만, 그 범위 안에서 이전 이력이 반복 전송되는 비용을 없애지는 않습니다\.

- **B.** API 호출들이 같은 시간 예산을 소비하지만, 취소 신호를 받지 않는 저장소 읽기까지 즉시 중단시키지는 않습니다\.

- **C.** 공유 신호가 만료되면 진행 중인 파일 읽기와 JSON 파싱도 선점되므로, 실행 종료 시각을 정확히 보장합니다\.

#### 심화3. GMS가 완료 상태의 JSON을 반환하더라도, API용 스키마 뒤의 로컬 검증을 제거하려면 어떤 동등성을 먼저 입증해야 하나요?

##### 보기별 해설

- **A.** API 측 검증이 원래 스키마의 사용자 정의 제약까지 같은 의미로 강제한다는 동등성을 입증해야 합니다\.

  > 원래 스키마에는 사용자 정의 검증이 포함되어 있으며, API 요청은 strict 모드도 사용하지 않습니다\. 변환된 스키마의 전달만으로 원래 계약 전체가 강제된다고 볼 수 없어 의미적 동등성 확인이 필요합니다\.

- **B.** 응답의 완료 상태가 생성 성공을 나타내므로, HTTP 성공 여부와 일치한다는 사실만 입증하면 됩니다\.

  > 완료 상태와 HTTP 성공은 요청 처리의 성공을 나타내는 정보이지 애플리케이션 데이터 계약의 충족 증명이 아닙니다\. 정상적으로 생성된 응답도 원래 스키마의 제약을 위반할 수 있습니다\.

#### 심화4. GMS 러너와 호출자를 따로 배포할 때, 새 공급자의 인증 장애에도 기존 복구 정책을 보존하려면 어떤 배포 조건이 필요한가요?

JSON 문법이 올바르다는 것과 필드·타입·업무 규칙이 올바르다는 것은 별개입니다\. \- \*\*계약의 표현력 차이\*\*: 내부 검증 규칙을 외부 스키마로 변환하면 모든 규칙이 그대로 표현되지 않을 수 있습니다\. 따라서 외부 전달용 스키마와 최종 수용 기준을 구분해야 합니다\. \*\*이번 코드에 적용하면\*\* GMS는 단계별 Zod 스키마를 JSON Schema로 변환해 보내지만, 요청의 \`strict\`는 \`false\`입니다\. 따라서 이 코드만으로 서버가 스키마 준수를 강제한다고 볼 수 없습니다\. 또한 변환에 \`unrepresentable: 'any'\`를 사용하며, 원본 스키마에는 선택지 순서·중복 여부나 문제 난이도 개수처럼 사용자 정의 \`refine\` 검증도 있습니다\. 외부에 전달하는 JSON Schema만으로 원본 검증 전체를 대체할 수는 없습니다\. 그래서 최종 출력은 \`JSON\.parse\(text\)\`로 문법을 확인한 뒤, 원본인 \`schema\.parse\(\.\.\.\)\`로 다시 검사합니다\. 이 검사에서 실패하면 정상 결과로 반환하지 않고 \`invalid\_output\` 실패로 처리합니다\. 즉, \*\*원격 스키마는 생성 제약이고 로컬 스키마는 최종 수용 기준\*\*입니다\. 다만 로컬 검증도 답변의 사실성이나 코드 분석의 정확성까지 보장하는 것은 아닙니다\.

#### 코드 근거

- src/gms\.ts:20–21, 31–32 — \`phaseSchemas\[phase\]\`를 JSON Schema로 변환하고 Responses API의 \`text\.format\`에 \`strict: false\`로 전달합니다\.
- src/contracts\.ts:29–46 — 선택지 순서, 정규화한 선택지 텍스트의 중복, 초기 문제의 난이도 구성 등을 \`refine\`으로 검사합니다\. 7–11행에는 저장소 경로의 사용자 정의 검증도 있습니다\.
- src/gms\.ts:43–51, 71–73 — 응답 외피와 완료 상태를 검사한 다음 최종 텍스트에 \`schema\.parse\(JSON\.parse\(text\)\)\`를 적용합니다\. Zod 오류나 JSON 문법 오류는 \`invalid\_output\`으로 변환합니다\.
- src/codex\.ts:6–12 — GMS가 사용하는 단계별 스키마는 \`contracts\.ts\`의 공통 계약입니다\. src/contracts\.ts:12, 69의 답변 계약은 필수 문자열의 길이, 근거 배열의 최대 개수, 허용 필드를 제한합니다\.

#### 참고

정적 코드만 확인했습니다\. 실제 GMS 서버의 스키마 강제 수준이나 실행 결과는 검증하지 않았으며, 코드 수정·테스트·스크립트 실행 및 인증·호스트 파일 열람은 하지 않았습니다\.

### s1 · hey-lookup.md

모델이 요청한 파일 읽기는 \*\*\`src/gms\.ts\`의 \`Gms\.run\(\)\`이 요청을 받아 분기하고, \`src/source\-reader\.ts\`의 \`RepositoryReader\.read\(\)\`가 실제로 처리합니다\.\*\* GMS 서버에 로컬 파일 접근을 맡기는 구조가 아닙니다\. 관련 CS 개념은 \*\*도구 호출\(function calling\)\*\*입니다\. 모델은 실행할 함수의 이름과 인자를 반환하고, 애플리케이션이 이를 검증한 뒤 실제 함수를 실행하여 결과를 돌려주는 방식입니다\. 이 코드에서는 다음처럼 적용됩니다\. 1\. \`Gms\.run\(\)\`이 API 응답에서 \`function\_call\` 항목을 추출합니다\. 2\. \`read\_file\` 또는 \`read\_base\_file\`이면 인자를 검증하고, 각각 현재 소스용 \`reader\` 또는 기준 소스용 \`base\`의 \`\.read\(path, start, limit\)\`를 호출합니다\. 3\. \`RepositoryReader\.read\(\)\`가 경로·파일 종류·크기 등을 검사한 뒤 \`readFile\(\)\`로 내용을 읽습니다\. \`redact\(\)\`를 적용하고 요청한 줄 범위를 반환합니다\. 4\. 읽은 결과는 \`function\_call\_output\`으로 대화 입력에 추가되어 다음 GMS API 요청에 전달됩니다\. 읽기에 실패하면 일반화된 오류 결과를 반환합니다\.

#### 코드 근거

- \`src/gms\.ts:17\` — 현재 작업의 \`source\`와 그 형제 디렉터리인 \`base\`에 대해 각각 \`RepositoryReader\`를 생성합니다\.
- \`src/gms\.ts:46–61\` — 모델 응답의 \`function\_call\`을 추출하고, \`read\_file\`·\`read\_base\_file\`을 해당 reader의 \`\.read\(\)\`로 연결합니다\. 읽기 인자의 기본값과 범위는 9행에 정의되어 있습니다\.
- \`src/source\-reader\.ts:19–24\` — \`safePath\`, 줄 범위, 실제 경로, 일반 파일 여부, 심볼릭 링크 여부, 파일 크기를 검사한 뒤 \`readFile\(dest, 'utf8'\)\`을 실행하고 줄 단위 결과를 만듭니다\.
- \`src/gms\.ts:65–66\` — 처리 실패는 \`Source request refused or unavailable\`로 반환하고, 결과를 \`call\_id\`가 연결된 \`function\_call\_output\`으로 추가합니다\. 다음 API 요청에서 이 입력을 보내는 부분은 27–32행입니다\.

#### 참고

위 내용은 관련 소스의 정적 확인 결과입니다\. 코드 수정이나 테스트·스크립트 실행은 하지 않았으며, 실제 GMS 연동 동작과 \`safePath\`·\`redact\`의 내부 구현은 검증하지 않았습니다\.

### s1 · hey-wrongPremise.md

잘린 JSON을 복구하는 방식이 아닙니다\. 현재 코드는 \*\*응답이 한도를 넘으면 파싱하지 않고 실패 처리\*\*합니다\. \*\*관련 CS 원리 — 자원 제한과 조기 실패\(fail\-fast\):\*\* 외부 입력을 누적할 때 크기 상한을 검사하고, 초과하면 즉시 처리를 중단해 메모리 사용과 파싱 부담을 제한하는 방식입니다\. JSON 앞부분만 남긴다고 유효한 JSON이 보장되지는 않습니다\. \*\*이번 코드의 동작:\*\* \- 응답 청크의 바이트 수를 누적하다가 \*\*2 MiB를 초과하면\*\* \`ModelFailure\`의 \`invalid\_output\`을 던집니다\. 초과한 청크를 저장하거나 앞부분만 파싱하지 않습니다\. \- 스트림을 끝까지 읽고 한도 이내인 경우에만 청크 전체를 합쳐 \`JSON\.parse\`합니다\. \- 그 뒤 추출한 최종 답변 텍스트에도 \*\*512,000바이트\*\* 제한을 적용합니다\. 여기서도 자르지 않고 실패 처리합니다\. \- 서버에서 이미 잘린 JSON이 도착해 \`JSON\.parse\`가 실패하는 경우에도, 복구하지 않고 \`invalid\_output\`으로 분류합니다\. 따라서 이 경로에는 괄호를 보충하거나 부분 JSON을 살려 쓰는 복구 로직이 없습니다\. 호출부는 오류를 HTTP 422의 \`model\_failure\` 응답으로 전달합니다\.

#### 코드 근거

- src/gms\.ts:39–43 — 청크 크기를 누적하고 2 \* 1024 \* 1024 초과 시 예외를 던집니다\. JSON\.parse는 수신 루프가 정상 종료된 뒤에만 실행됩니다\.
- src/gms\.ts:48–51 — output\_text를 합친 뒤 512000바이트 초과 여부를 검사하고, 통과한 텍스트만 JSON 파싱 및 스키마 검증합니다\.
- src/gms\.ts:71–73 — 기존 ModelFailure는 그대로 전파하고, SyntaxError 및 ZodError는 invalid\_output으로 변환합니다\.
- src/runner\-server\.ts:27–32 — model\.run 호출에서 발생한 오류를 HTTP 422와 \{ error: 'model\_failure', failure: \.\.\. \}로 반환합니다\.

#### 참고

코드 정적 확인만 수행했습니다\. 테스트·스크립트는 실행하지 않았으므로 실제 GMS의 응답 절단 여부나 런타임 동작은 검증하지 않았습니다\.

### Q1 · ✅ 정답

#### Q1. 최초 질문과 여러 심화 질문 묶음이 함께 있을 때, 해설 공개 범위를 질문 스레드에 연결한 이번 변경의 핵심 효과는 무엇인가요?

요청한 스레드의 질문 댓글에 담긴 질문만 공개하여 다른 묶음과 섞이지 않게 합니다\.

##### 답변 평가

B는 확정 정답과 일치하며, 신뢰할 수 있는 질문 댓글의 식별자를 읽어 해당 질문만 공개한다는 이유도 코드와 부합합니다\. 특히 공개 범위가 최신 묶음이나 전체 질문 목록이 아니라 요청한 스레드의 질문 댓글로 결정된다는 핵심을 정확히 설명했습니다\.

##### 해설

범위 제한\(scoping\)은 작업 대상을 특정 문맥에 속한 항목으로 한정하는 원리이며, 참조 검증\(reference validation\)은 식별자가 실제 저장된 대상과 대응하는지 확인하는 과정입니다\. 이 코드에서는 요청 스레드의 신뢰할 수 있는 질문 댓글 하나를 찾고, 버전 표식과 저장된 질문에 대한 참조를 확인한 뒤 그 댓글에 담긴 질문만 공개 대상으로 반환합니다\. 따라서 개별 질문 댓글에서는 해당 질문만, 심화 묶음 댓글에서는 그 묶음의 질문만 공개하는 B가 정답이며, 같은 코드 버전이라는 조건만으로 다른 묶음까지 포함하지 않습니다\.

##### 보기별 해설

  > 틀립니다\. 공개 경로는 최초 질문 전체를 선택하지 않고, 요청 스레드에서 확인한 질문 댓글의 참조만 공개 대상으로 사용합니다\.

- **B.** 요청한 스레드의 질문 댓글에 담긴 질문만 공개하여 다른 묶음과 섞이지 않게 합니다\.

  > 맞습니다\. 요청 스레드의 신뢰할 수 있는 질문 댓글에서 질문 참조를 추출하고 저장된 질문과 대조하므로, 그 댓글에 포함된 개별 질문 또는 심화 묶음으로 공개 범위가 제한됩니다\.

- **C.** 요청한 스레드와 관계없이 가장 최근에 생성된 질문 묶음의 해설을 공개합니다\.

  > 틀립니다\. 최신 생성 순서는 공개 범위의 선택 기준이 아니므로, 현재 코드 버전에서 이전에 생성된 묶음의 스레드에 요청하면 그 묶음이 대상입니다\.

- **D.** 같은 코드 버전에서 생성된 질문이라면 모든 묶음의 해설을 함께 공개합니다\.

#### Q2. 명령 사용 권한이 있는 사람이 봇 질문 표식을 새 사용자 댓글에 복사해도, 이를 해설 범위의 근거로 삼지 않는 이유는 무엇인가요?

##### 답변 평가

신뢰 경계에서는 요청자의 권한과 입력 자료의 출처를 구분해야 합니다\. 이번 코드는 명령 사용 권한을 확인하는 것과 별개로, 봇 소유이거나 저장된 봇 게시 이력으로 확인되는 댓글만 해설 범위 판별에 전달하므로 복사한 표식만으로는 근거가 되지 않습니다\.

##### 보기별 해설

- **A.** 유효한 질문 표식이 있다는 사실만으로 봇이 게시한 댓글임을 증명할 수 있기 때문입니다\.

  > 질문 표식은 질문을 식별하는 형식이며 누구나 텍스트로 복사할 수 있습니다\. 표식의 유효성은 댓글이 봇에게서 나왔다는 증거가 아닙니다\.

- **B.** 명령 사용 권한이 있으면 사용자 댓글도 봇이 게시한 질문으로 취급해야 하기 때문입니다\.

  > 명령 사용 권한은 요청을 처리해도 되는지를 판단합니다\. 그 권한이 사용자가 작성한 댓글을 신뢰할 수 있는 봇 게시물로 바꾸지는 않습니다\.

- **C.** 현재 코드 버전의 질문을 복사하면 댓글 출처 확인을 생략할 수 있기 때문입니다\.

  > 코드 버전 일치는 질문이 현재 코드에 대응하는지를 확인할 뿐입니다\. 현재 질문을 복사했더라도 댓글 출처에 대한 신뢰 확인은 별도로 필요합니다\.

- **D.** 명령을 요청할 권한과 해설 범위의 근거가 되는 댓글의 신뢰성은 별도로 확인해야 하기 때문입니다\.

### 심화2 · ❌ 오답

이전에 게시된 질문의 정체성을 유지하여 현재 같은 번호를 가진 다른 질문의 해설로 바뀌는 것을 막습니다\.

##### 답변 평가

식별자로 이전 댓글의 질문을 구별할 수 있다는 설명은 맞지만, 최신 Q1의 해설로 통일해야 한다는 결론은 틀립니다\. 질문의 정체성\(identity\)과 표시용 번호\(positional label\)를 혼동한 것으로, 번호는 재사용될 수 있으므로 최신 번호에 맞추면 이전 댓글과 원래 질문의 대응을 오히려 깨뜨립니다\. 선택한 C는 확정 정답 D와 다르며, 구현도 저장된 질문을 댓글의 식별자로 찾아 연결합니다\.

##### 해설

객체 정체성\(object identity\)은 대상을 다른 대상과 구별하는 기준이며, 표시용 번호는 배치상의 위치를 나타낼 뿐 같은 대상임을 보장하지 않습니다\. 이 코드의 질문 식별자는 코드 버전·질문 문장·위치·보기를 해시한 참조이고, 구현은 현재 질문과 같은 코드 기준의 저장 이력을 합쳐 댓글의 식별자에 대응하는 질문을 찾습니다\. 따라서 D가 정답이며, 이전 질문이 저장되어 있다면 새 Q1과 구별하여 원래 질문의 해설을 제공하고, 대응하는 저장 질문이 없으면 최신 Q1로 대체하지 않고 공개를 거절합니다\.

  > 식별자는 저장 질문을 찾는 참조이지 정답과 해설을 복원할 수 있는 데이터가 아닙니다\. 댓글의 식별자에 대응하는 저장 질문이 없으면 구현은 오류를 반환합니다\.

- **B.** 코드 버전이 같으면 이전 Q1과 새 Q1은 동일한 질문으로 취급할 수 있습니다\.

  > 코드 버전이 같아도 질문 문장이나 보기가 달라지면 다른 질문일 수 있습니다\. 식별자 계산에는 코드 버전뿐 아니라 질문 문장·코드 위치·보기도 포함됩니다\.

#### 심화4. 저장된 심화 질문은 있지만 게시 좌표가 없는 구버전 작업을 재개할 때, 질문을 다시 생성하지 않고 고정된 diff에서 좌표를 보충하는 이점은 무엇인가요?

- **B.** 같은 코드로 모델을 다시 호출해도 질문 내용은 같으므로 재생성과 결과 재사용의 보장은 같습니다\.

### s4 · hey-design.md

핵심은 \*\*해설 공개 대상을 사용자가 보고 있는 질문 댓글에 고정해, 최초 질문과 여러 심화 질문 묶음이 섞이지 않게 하려는 것\*\*입니다\. 관련 CS 개념은 \*\*컨텍스트 기반 범위 지정\(scoping\)\*\*입니다\. 작업 대상의 경계를 해당 요청이 속한 문맥에 연결하는 원리입니다\. 이전 구현은 명령 인자의 질문 번호로 대상을 고르고, 인자가 없으면 답글 위치와 무관하게 최초 질문 전체를 선택했습니다\. 따라서 심화 질문 스레드에서 요청해도 인자가 없으면 최초 질문의 해설이 나오는 구조였습니다\. 변경 후에는 인자를 받지 않고, 답글이 달린 스레드의 질문 댓글에 기록된 질문 ID만 저장된 질문과 연결합니다\. 질문 댓글에 한 문항이 있으면 그 문항만, 한 묶음이 있으면 그 묶음만 공개하며, 가장 최근 묶음이나 같은 코드 버전의 모든 질문으로 범위를 넓히지 않습니다\. 또 다른 개념은 \*\*신뢰 경계\(trust boundary\)\*\*입니다\. 요청자의 권한과 대상 데이터의 신뢰성은 별도로 검증해야 한다는 원리입니다\. 이번 코드는 명령 사용 권한을 확인한 뒤에도, 봇 소유 또는 게시 이력으로 확인된 댓글만 범위의 근거로 전달합니다\. 따라서 사용자가 질문 표식을 복사한 댓글은 범위의 근거가 되지 않습니다\. 스레드가 없거나 여러 질문 묶음이 섞여 범위가 모호하거나, 코드 버전·저장된 질문을 확인할 수 없는 경우에도 임의의 다른 묶음으로 대체하지 않고 거절합니다\. 즉, 개별 질문을 인자로 자유롭게 선택하는 기능 대신 \*\*‘이 질문 댓글의 해설’이라는 명확하고 검증 가능한 연결\*\*을 택한 변경입니다\. 이는 변경 전후 코드와 테스트에 명시된 기대 동작으로 확인한 해석이며, 작성자의 별도 의사결정 기록이나 실제 운영 효과는 확인하지 못했습니다\.
