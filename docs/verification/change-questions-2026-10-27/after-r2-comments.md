##### 해설

기존 Codex 경로는 CLI의 도구 제한과 스냅샷 도구 연결을 설정했지만, 새 GMS 경로는 러너가 모델의 도구 요청을 직접 처리합니다\. 이때 모델 출력은 권한 부여가 아니며, <b>허용된 도구와 스냅샷 경로 검증</b>이 접근 경계를 지킵니다\. 이를 모델의 지시 준수에만 맡긴 것으로 이해하면, 직접 호출로 전환하며 유지해야 할 보안 경계를 잘못 검토하게 됩니다\.

##### 보기별 해설

- **A.** GMS 인증 키에 부여된 권한이 러너에서 읽을 수 있는 파일 범위를 결정합니다\.

  > API 인증과 로컬 파일 접근 권한을 혼동한 보기입니다\. GMS 키는 외부 API 요청에 사용되고, 파일 접근은 러너에 생성된 RepositoryReader와 도구 분기에서 제한됩니다\.

- **B.** 모델이 저장소 문구를 작업에 필요하다고 판단하면 해당 파일까지 읽기 범위가 확장됩니다\.

  > 모델의 판단이 파일 접근 권한을 확장한다고 읽은 보기입니다\. 모델이 경로를 요청하더라도 판독기는 안전한 상대 경로인지, 실제 대상이 해당 스냅샷 루트 안에 있는지 검증합니다\.

구방식으로 저장된 해설은 게시하지 않고 질문 스레드에서 새 요청을 받도록 안내해야 합니다\.

C를 골라 구방식 본문을 게시하지 않고 새 요청을 안내해야 한다는 정책은 맞게 이해했습니다\. <b>정답은 맞지만 이유가 다릅니다</b>: 코드 버전 비교는 해설 본문이 아니라 headSha·baseSha·startSha만 비교하므로, 구방식 본문이라고 항상 불일치하지는 않습니다\(src/learning\.ts:4\~5\)\. 실제 차단은 코드 버전 검사에 앞서 revealThreadVersion이 1이 아닌 저장 결과에 안내문을 답글로 남기고 반환하는 별도 검사입니다\(src/learning\-command\.ts:97\~103\)\.

##### 해설

변경 전에는 코드 버전만 같으면 저장된 해설을 재게시할 수 있었지만, 이제는 구방식으로 만들어진 공개 결과의 재사용도 차단합니다\. <b>코드 기준의 일치와 공개 범위의 일치는 별개</b>이므로, 이 경계를 없애면 배포 직후 재개된 작업이 스레드 밖 질문의 해설까지 공개할 수 있습니다\.

##### 보기별 해설

- **A.** 코드 버전이 일치하므로 저장된 해설 본문을 그대로 게시해야 합니다\.

  > 코드 버전 검사를 공개 범위 검증으로 오해한 판단입니다\. 새 코드는 코드 버전 비교와 별도로 저장된 해설이 새 공개 방식으로 생성되었는지 확인합니다\.

- **B.** 현재 요청 스레드에 게시하면 저장된 본문의 공개 범위도 그 스레드에 맞게 제한됩니다\.

  > 게시 위치가 이미 생성된 본문의 내용을 좁혀 주지는 않습니다\. 저장된 본문에는 다른 질문의 해설이 포함될 수 있으므로 새 코드는 이를 그대로 답글로 게시하지 않습니다\.

- **C.** 구방식으로 저장된 해설은 게시하지 않고 질문 스레드에서 새 요청을 받도록 안내해야 합니다\.

  > 저장된 공개 결과에 새 방식의 버전 표시가 없으면 안내문을 답글로 남기고 반환합니다\. 새 요청을 받아야 현재 스레드에 근거한 범위 판정을 거칠 수 있습니다\.

- **D.** 저장된 결과에 새 방식의 버전 표시를 추가하면 본문을 재검토하지 않고 게시할 수 있습니다\.

#### 심화2. 이번 변경은 심화 질문을 게시할 때 별도의 질문 스레드 정보를 전달합니다\. 사용자가 기존 질문 스레드에서 심화 생성을 요청했다고 가정할 때, 이 정보를 없애고 기존 답글 게시 경로만 사용하자는 단순화 제안을 어떻게 평가해야 하나요? 목표는 생성된 각 묶음을 답글로 구분해 해설을 요청할 수 있게 하는 것입니다\.

기존 스레드에 새 묶음이 합쳐질 수 있으므로 별도 스레드를 만드는 게시 경로를 유지해야 합니다\.

##### 답변 평가

독립된 스레드가 묶음의 범위 구분에 도움이 된다는 이해는 맞습니다\. 다만 동작을 잘못 읽었습니다\. 변경 후에는 <b>showanswer에 번호 인자를 받지 않으며</b>\(src/commands\.ts:22\~23\), 같은 스레드에서 질문 원본 댓글이 여러 개 발견되면 번호로 고르지 않고 해설 요청을 거절합니다\(src/question\-thread\.ts:13\~19\)\. 따라서 B가 아니라 A이며, 기존 부모·discussion에 답하기보다 새 질문 스레드 생성을 우선하는 경로를 유지해야 합니다\(src/platform\.ts:69\~78\)\.

##### 해설

변경 전의 일반 답글 경로는 요청이 있던 스레드를 재사용했지만, 이제 심화 질문 묶음은 <b>독립된 답글 가능 스레드</b>로 게시됩니다\. 이는 번호 인자가 없어진 해설 명령의 범위 판정과 연결되므로, 게시 경로만 단순화하면 여러 묶음이 섞여 해설을 요청하지 못할 수 있습니다\.

##### 보기별 해설

- **A.** 기존 스레드에 새 묶음이 합쳐질 수 있으므로 별도 스레드를 만드는 게시 경로를 유지해야 합니다\.

  > 질문 스레드 정보가 있으면 기존 부모나 discussion에 답하는 경로보다 새 스레드 생성 경로가 우선합니다\. 범위 판정은 한 스레드에서 여러 질문 원본 댓글이 발견되면 거절하므로 이 분리가 중요합니다\.

- **B.** 심화 번호가 묶음마다 다르므로 같은 스레드에 게시해도 묶음별 해설 요청을 구분할 수 있습니다\.

  > 표시 번호를 공개 대상 선택자로 오해한 판단입니다\. 새 해설 명령은 번호를 받지 않으며 같은 스레드의 여러 원본 중 번호로 묶음을 고르지 않습니다\.

- **C.** 별도 스레드는 GitHub에서만 필요하므로 GitLab에서는 기존 discussion에 답글로 게시해도 됩니다\.

  > GitLab의 discussion 식별자를 묶음 구분보다 더 세밀한 식별자로 오해한 판단입니다\. 같은 discussion에 원본 묶음 둘을 게시하면 범위가 모호해지므로 GitLab도 새 discussion을 생성합니다\.

- **D.** 줄 좌표가 없는 변경은 독립된 질문 스레드를 만들 수 없으므로 일반 댓글로 게시해야 합니다\.

  > 줄 좌표가 없다는 사실을 답글 가능한 게시 위치가 없다는 뜻으로 오해한 판단입니다\. GitHub에서는 파일 수준 리뷰 댓글을 사용하고, GitLab의 새 discussion 생성은 줄 좌표를 요구하지 않습니다\.

#### 심화1. 변경 전 워커가 최초 질문 전체의 해설 본문을 저장한 뒤 게시 전에 중단되었고, 배포 후 새 워커가 그 작업을 재개한다고 가정하겠습니다\. 코드 버전은 그대로이며 요청은 개별 질문 스레드에서 작성되었습니다\. 이번 변경의 공개 범위를 지키기 위한 재개 정책으로 가장 적절한 것은 무엇인가요?

구방식으로 저장된 해설은 게시하지 않고 질문 스레드에서 새 요청을 받도록 안내해야 합니다\.

##### 해설

변경 전에는 코드 버전만 같으면 저장된 해설을 재게시할 수 있었지만, 이제는 구방식으로 만들어진 공개 결과의 재사용도 차단합니다\. <b>코드 기준의 일치와 공개 범위의 일치는 별개</b>이므로, 이 경계를 없애면 배포 직후 재개된 작업이 스레드 밖 질문의 해설까지 공개할 수 있습니다\.

##### 보기별 해설

- **A.** 코드 버전이 일치하므로 저장된 해설 본문을 그대로 게시해야 합니다\.

  > 코드 버전 검사를 공개 범위 검증으로 오해한 판단입니다\. 새 코드는 코드 버전 비교와 별도로 저장된 해설이 새 공개 방식으로 생성되었는지 확인합니다\.

- **B.** 현재 요청 스레드에 게시하면 저장된 본문의 공개 범위도 그 스레드에 맞게 제한됩니다\.

  > 게시 위치가 이미 생성된 본문의 내용을 좁혀 주지는 않습니다\. 저장된 본문에는 다른 질문의 해설이 포함될 수 있으므로 새 코드는 이를 그대로 답글로 게시하지 않습니다\.

- **C.** 구방식으로 저장된 해설은 게시하지 않고 질문 스레드에서 새 요청을 받도록 안내해야 합니다\.

  > 저장된 공개 결과에 새 방식의 버전 표시가 없으면 안내문을 답글로 남기고 반환합니다\. 새 요청을 받아야 현재 스레드에 근거한 범위 판정을 거칠 수 있습니다\.

- **D.** 저장된 결과에 새 방식의 버전 표시를 추가하면 본문을 재검토하지 않고 게시할 수 있습니다\.

  > 버전 표시를 본문을 안전하게 바꾸는 변환으로 오해한 판단입니다\. 이 표시는 새 범위 판정으로 생성된 결과에 붙는 것이며, 구본문에 표시만 덧붙이는 호환 처리는 구현되어 있지 않습니다\.

#### 심화2. 이번 변경은 심화 질문을 게시할 때 별도의 질문 스레드 정보를 전달합니다\. 사용자가 기존 질문 스레드에서 심화 생성을 요청했다고 가정할 때, 이 정보를 없애고 기존 답글 게시 경로만 사용하자는 단순화 제안을 어떻게 평가해야 하나요? 목표는 생성된 각 묶음을 답글로 구분해 해설을 요청할 수 있게 하는 것입니다\.

기존 스레드에 새 묶음이 합쳐질 수 있으므로 별도 스레드를 만드는 게시 경로를 유지해야 합니다\.

##### 해설

변경 전의 일반 답글 경로는 요청이 있던 스레드를 재사용했지만, 이제 심화 질문 묶음은 <b>독립된 답글 가능 스레드</b>로 게시됩니다\. 이는 번호 인자가 없어진 해설 명령의 범위 판정과 연결되므로, 게시 경로만 단순화하면 여러 묶음이 섞여 해설을 요청하지 못할 수 있습니다\.

##### 보기별 해설

- **A.** 기존 스레드에 새 묶음이 합쳐질 수 있으므로 별도 스레드를 만드는 게시 경로를 유지해야 합니다\.

  > 질문 스레드 정보가 있으면 기존 부모나 discussion에 답하는 경로보다 새 스레드 생성 경로가 우선합니다\. 범위 판정은 한 스레드에서 여러 질문 원본 댓글이 발견되면 거절하므로 이 분리가 중요합니다\.

- **B.** 심화 번호가 묶음마다 다르므로 같은 스레드에 게시해도 묶음별 해설 요청을 구분할 수 있습니다\.

  > 표시 번호를 공개 대상 선택자로 오해한 판단입니다\. 새 해설 명령은 번호를 받지 않으며 같은 스레드의 여러 원본 중 번호로 묶음을 고르지 않습니다\.

- **C.** 별도 스레드는 GitHub에서만 필요하므로 GitLab에서는 기존 discussion에 답글로 게시해도 됩니다\.

  > GitLab의 discussion 식별자를 묶음 구분보다 더 세밀한 식별자로 오해한 판단입니다\. 같은 discussion에 원본 묶음 둘을 게시하면 범위가 모호해지므로 GitLab도 새 discussion을 생성합니다\.

- **D.** 줄 좌표가 없는 변경은 독립된 질문 스레드를 만들 수 없으므로 일반 댓글로 게시해야 합니다\.

  > 줄 좌표가 없다는 사실을 답글 가능한 게시 위치가 없다는 뜻으로 오해한 판단입니다\. GitHub에서는 파일 수준 리뷰 댓글을 사용하고, GitLab의 새 discussion 생성은 줄 좌표를 요구하지 않습니다\.

#### 심화3. GitLab에서는 같은 봇 질문 note가 일반 댓글 목록과 discussion 목록 양쪽에서 조회될 수 있습니다\. 새 해설 범위 판정이 조회 중복에는 견디면서 실제로 묶음이 섞인 스레드는 구별하는지 확인하려고 합니다\. 모든 질문이 현재 코드 버전에 저장되어 있다고 가정하면 어떤 검증이 가장 적절한가요?

같은 note의 중복 표현과 서로 다른 두 원본 note를 대조해 전자는 공개되고 후자는 거절되는지 확인합니다\.

##### 해설

변경 전에는 저장된 질문과 번호로 공개 대상을 골랐지만, 이제는 게시된 원본 댓글이 범위의 근거가 됩니다\. 따라서 <b>같은 댓글의 중복 조회와 서로 다른 원본의 혼재</b>를 구별해야 하며, 이를 혼동하면 정상 요청을 막거나 모호한 요청의 공개 범위를 임의로 정하게 됩니다\.

##### 보기별 해설

- **A.** 서로 다른 discussion에서 가져온 질문을 한꺼번에 전달해 전체 해설이 나오는지 확인합니다\.

  > 조회된 모든 질문을 공개 후보로 합치는 것으로 오해한 검증입니다\. 새 판정은 먼저 요청과 같은 surface 및 스레드에 속하는 댓글로 후보를 제한합니다\.

- **B.** 같은 note의 중복 표현과 서로 다른 두 원본 note를 대조해 전자는 공개되고 후자는 거절되는지 확인합니다\.

  > 댓글 식별 키로 같은 note의 중복 표현을 제거한 뒤 원본 후보 수를 검사합니다\. 같은 note가 두 번 조회되는 경우와 식별자가 다른 원본 둘이 같은 discussion에 있는 경우를 대조해야 이 경계를 확인할 수 있습니다\.

- **C.** 같은 discussion에 원본 둘을 넣고 가장 최근 원본의 해설만 나오는지 확인합니다\.

  > 모호성을 최신 원본 우선으로 해결한다고 오해한 검증입니다\. 서로 다른 원본이 둘 이상 남으면 시간순으로 하나를 고르지 않고 범위를 정할 수 없다고 안내합니다\.

- **D.** 같은 discussion에 원본 둘을 넣고 저장된 질문들의 해설이 합쳐져 나오는지 확인합니다\.

  > 저장된 질문임이 확인되면 묶음 간 합집합 공개도 허용된다고 오해한 검증입니다\. 저장 데이터와의 대조에 앞서 원본이 하나인지 확인하므로 실제 원본 둘의 해설은 합쳐 공개하지 않습니다\.

#### 심화4. 이번 변경은 개별 질문과 심화 묶음에 코드 버전 표식을 추가하면서 요약 댓글과는 다른 표식을 사용합니다\. 이를 공통화하려고 질문 댓글에도 요약 댓글용 표식을 그대로 쓰자는 제안이 나왔습니다\. 같은 코드 버전의 요약과 심화 댓글이 모두 일반 댓글 조회에 나타난다고 가정할 때, 어떤 유지보수 판단이 맞나요?

요약 갱신의 대상 식별에도 쓰이는 표식이므로 질문 댓글과의 구분을 유지해야 합니다\.

##### 해설

이번 변경은 질문 댓글에도 버전 정보를 붙이지만, 기존 요약 식별 표식을 재사용하지는 않습니다\. 요약을 찾는 호출부가 그 표식을 사용하므로 <b>버전 확인과 요약 대상 식별을 분리</b>해야 하며, 공통화하면 질문 묶음이 요약 갱신 대상으로 선택될 수 있습니다\.

##### 보기별 해설

- **A.** 표식은 코드 버전만 나타내므로 같은 버전의 댓글끼리는 공통 표식을 써도 안전합니다\.

  > 표식의 소비자가 해설 범위 판정뿐이라고 오해한 판단입니다\. 요약 게시·갱신 경로도 요약용 버전 표식이 포함된 댓글을 찾습니다\.

- **B.** 질문 식별자가 요약 댓글을 구분하므로 표식을 공통화해도 갱신 대상은 달라지지 않습니다\.

  > 요약 검색이 항상 질문 식별자까지 대조한다고 오해한 판단입니다\. 현재 버전 표식으로 찾는 경로는 그 표식 자체를 사용하며, 질문 식별자 대조는 별도의 구형 요약 호환 경로에 있습니다\.

- **C.** 요약과 질문을 구분하려면 질문 댓글의 코드 버전 표식을 모두 제거해야 합니다\.

  > 역할 분리를 버전 정보 제거로 해결해야 한다고 오해한 판단입니다\. 새 코드는 별도 질문용 표식을 만들고 해설 범위 판정에서는 요약용과 질문용 표식을 모두 인식합니다\.

- **D.** 요약 갱신의 대상 식별에도 쓰이는 표식이므로 질문 댓글과의 구분을 유지해야 합니다\.

  > 질문용 표식은 같은 코드 버전을 나타내면서도 요약용 문자열과 구별됩니다\. 따라서 질문의 버전을 검사할 수 있고 기존 요약 검색이 심화 댓글을 요약으로 오인하는 위험도 피할 수 있습니다\.

#### 심화5. 변경 전 생성된 심화 질문 작업에 본문·문항·시작 번호는 저장되어 있지만 새 게시 좌표 정보는 없는 상태로 배포되었다고 가정하겠습니다\. 코드 버전은 그대로이고 외부 게시도 아직 없으며 고정된 소스는 준비할 수 있습니다\. 모델 재호출 없이 기존 문항을 보존하면서 새 게시 방식을 적용하려면 어떤 복구 방안이 적절한가요?

저장된 첫 문항과 해당 스냅샷의 diff에서 게시 위치를 복원해 기존 결과를 별도 스레드로 게시해야 합니다\.

##### 해설

변경 전의 저장된 질문 결과에는 새 스레드 게시 정보가 없지만, 이번 변경은 저장된 문항과 고정된 diff에서 이를 복원합니다\. <b>문항을 재생성하지 않고 게시 방식만 보완</b>하므로 기존 질문·번호를 유지할 수 있으며, 이를 구형 해설 결과와 같은 정책으로 취급하면 복구 가능한 작업까지 버리게 됩니다\.

##### 보기별 해설

- **A.** 새 게시 좌표가 없는 결과는 폐기하고 질문 생성 작업부터 다시 시작해야 합니다\.

  > 새 게시 정보의 부재를 질문 내용 자체의 무효로 오해한 판단입니다\. 재개 경로는 저장된 문항을 유지하고 소스 준비로 게시 위치만 얻으며 모델을 다시 호출하지 않습니다\.

- **B.** 저장된 첫 문항과 해당 스냅샷의 diff에서 게시 위치를 복원해 기존 결과를 별도 스레드로 게시해야 합니다\.

  > 저장된 결과에 문항이 있고 게시 정보가 없으면 해당 스냅샷의 소스를 준비해 첫 문항의 경로·side와 diff를 대조합니다\. 복원된 정보를 최종 게시 호출에 전달해 별도 질문 스레드 경로를 사용합니다\.

- **C.** 저장된 결과를 원래 요청 스레드에 일반 답글로 게시하는 것으로 복구를 끝내야 합니다\.

  > 내용 재사용과 예전 게시 방식 재사용을 같은 호환 처리로 오해한 판단입니다\. 새 코드는 기존 결과를 재사용하더라도 게시 정보를 복원해 요청 스레드에 합쳐지는 것을 피합니다\.

- **D.** 저장된 해설 공개 결과와 마찬가지로 기존 질문 결과도 새 요청을 받도록 안내하고 종료해야 합니다\.

  > 구형 해설 본문의 공개 범위 문제를 구형 질문 결과에도 동일하게 적용한 판단입니다\. 구형 해설은 재요청을 안내하지만, 질문 결과는 저장된 문항에서 게시 위치를 복원하는 별도 호환 경로를 갖습니다\.
