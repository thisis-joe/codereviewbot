- **B.** 파일 접근은 차단되고 도구 실패 결과로 대화를 이어갈 수 있어야 하며, 이후 정상 응답까지 막을 필요는 없습니다\.

#### 심화2. 기존 CLI 프로세스 실행 대신 GMS의 HTTP 요청과 로컬 도구 실행을 반복하게 되었습니다\. 운영 검증에서 네트워크 지연뿐 아니라 큰 스냅샷의 search\_text도 오래 걸린다고 가정하겠습니다\. timeoutMs를 실행 시간 제한으로 평가할 때 가장 정확한 판단은 무엇인가요?

##### 답변 평가

실행의 HTTP 라운드들이 하나의 시간 예산을 공유한다는 이해는 맞습니다\. 다만 B의 근거인 <b>검색에도 취소 신호가 전달된다</b>는 부분은 동작을 잘못 읽었습니다\. src/gms\.ts:62는 reader\.search에 검색어만 전달하고, src/source\-reader\.ts:26–36의 검색 구현에도 취소 신호를 받거나 확인하는 처리가 없으므로 진행 중인 검색이 제한 시간에 즉시 멈춘다고 보장할 수 없습니다\. 검색 후 다음 HTTP 라운드에 진입할 때 중단 여부를 확인하는 것\(src/gms\.ts:28\)은 검색 자체의 즉시 취소와 다르므로 D가 맞습니다\.

##### 해설

##### 보기별 해설

- **A.** HTTP 요청마다 제한 시간이 새로 시작되므로, 여러 도구 라운드를 합친 실행 시간은 별도의 총량 제한으로 통제해야 합니다\.

  > 시간 신호를 요청마다 생성한다고 오독한 보기입니다\. 신호는 반복문 밖에서 한 번 생성되며, 후속 HTTP 요청도 남아 있는 동일한 시간 예산을 사용합니다\.

- **B.** 실행 전체가 공유하는 신호가 파일 검색에도 전달되므로, 제한 시간에 진행 중인 검색이 중단되는지 확인해야 합니다\.

  > HTTP 요청에 전달되는 취소 신호가 파일 검색에도 전달된다고 오해한 보기입니다\. 검색 호출에는 검색어만 전달되므로, 제한 시간에 검색 자체가 즉시 중단되는 계약은 없습니다\.

- **C.** HTTP 응답 헤더를 받은 뒤에는 시간 제한이 적용되지 않으므로, 응답 본문과 도구 실행의 지연을 같은 방식으로 취급해야 합니다\.

  > fetch의 취소 신호가 헤더 수신까지만 적용된다고 오해한 보기입니다\. HTTP 본문 소비 중에도 신호의 영향을 받지만, 로컬 RepositoryReader 작업에는 같은 취소 연결이 없습니다\.

- **D.** HTTP 라운드는 하나의 시간 예산을 공유하지만, 진행 중인 로컬 검색까지 즉시 취소되는 보장으로 해석해서는 안 됩니다\.

  > 신호 생성은 반복문 밖에 있고 각 fetch가 그 신호를 사용하므로 HTTP 라운드마다 예산이 갱신되지 않습니다\. 반면 로컬 검색에는 신호가 전달되지 않으며, 다음 라운드 진입 시 중단 여부를 확인하는 것은 진행 중인 검색의 즉시 취소와 다릅니다\.

- **B.** 실행 전체가 공유하는 신호가 파일 검색에도 전달되므로, 제한 시간에 진행 중인 검색이 중단되는지 확인해야 합니다\.

- **D.** HTTP 라운드는 하나의 시간 예산을 공유하지만, 진행 중인 로컬 검색까지 즉시 취소되는 보장으로 해석해서는 안 됩니다\.

- **B.** 상태 조회만으로는 임대가 연장되지 않아 만료 후 작업 획득 절차에서 회수할 수 있습니다\.

##### 해설

##### 보기별 해설

- **A.** 두 리뷰 모두 기존 단계와 중간 파일 참조를 유지해 중단 지점에서 재개합니다\.

  > 단계 기록이 남아 있으면 필요한 입력도 계속 유효하다고 보는 오독입니다\. 결과가 없는 실패 리뷰는 단계·상태·진행 데이터를 초기화하므로, 정리됐을 수 있는 중간 파일 참조를 재사용하지 않습니다\.

- **B.** 두 리뷰 모두 기존 결과와 중간 진행 정보를 버리고 준비 단계부터 재개합니다\.

  > 결과가 없는 리뷰에 추가된 초기화를 모든 실패 리뷰로 확대한 해석입니다\. 정상 결과가 저장된 리뷰는 그 결과와 진행 정보를 유지하고 게시 가능한 상태로 돌아갑니다\.

- **C.** 정상 결과가 있는 리뷰는 다시 생성하고, 결과가 없는 리뷰는 기존 중간 파일 참조로 재개합니다\.

- **D.** 정상 결과가 있는 리뷰는 게시 경로로 재개하고, 결과가 없는 리뷰는 중간 진행 정보를 비워 준비부터 재개합니다\.

  > 재시도 갱신은 정상 결과가 있는 리뷰를 게시 대기 경로로 보내고, 결과가 없는 리뷰의 단계·상태·진행 데이터를 함께 초기화합니다\. 이후 작업 획득 시 초기 단계가 선택되므로 오래된 파일 참조에 기대지 않고 준비부터 재개합니다\.

### s2 · hey-design.md

##### 이유

#### 심화1. 이번 변경 후 운영 도구에서 Store\.retry를 호출하는 상황을 가정하겠습니다\. 두 review 작업 모두 작업 상태는 failed이지만, 하나에는 생성 실패 보고서가, 다른 하나에는 생성에 성공했으나 게시하지 못한 보고서가 저장되어 있습니다\. 운영 도구가 두 작업을 모두 ‘저장된 결과 게시 재시도’로 안내해도 되는지 판단할 때, 가장 적절한 설명은 무엇인가요?

##### 해설

변경 전에는 저장된 결과가 있는 review 작업을 일괄적으로 게시 단계로 돌려, 생성 실패 안내만 다시 게시할 수 있었습니다\. 이제는 <b>생성 실패 결과를 폐기하고 재생성</b>하되 성공적으로 생성한 결과는 보존하므로, 운영 도구가 모두 게시 재시도라고 안내하면 모델 실행과 복구 범위를 잘못 설명하게 됩니다\.

##### 보기별 해설

- **A.** 두 작업 모두 저장된 보고서를 게시하므로, 모델 재호출 없이 복구된다고 안내해도 됩니다\.

  > 결과의 존재만으로 게시 단계를 선택하던 변경 전 동작을 적용한 해석입니다\. 변경 후에는 결과 보고서의 상태가 failed이면 result와 diff를 비우고 생성 대기 상태로 돌립니다\.

- **B.** 두 작업 모두 기존 보고서를 폐기하므로, 질문 생성부터 다시 진행한다고 안내해야 합니다\.

  > 생성 실패 결과를 지우는 처리를 모든 결과에 적용한 해석입니다\. 성공적으로 생성된 비명령 작업의 결과는 보존하며, 다음 claim에서 게시 단계로 진입합니다\.

- **C.** 생성 실패 보고서는 재생성하고 생성 성공 보고서는 게시를 재시도하므로, 복구 단계가 다르다고 안내해야 합니다\.
