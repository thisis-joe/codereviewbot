# 질문봇 운영과 복구

코드 품질 검토는 작성자가 작성 단계에서 수행한다. 봇은 변경 이해 질문과 학습 해설을 담당하며, 자동 결함 탐색·수정 제안·CI 결과 보고를 수행하지 않는다.

## hey 이름 전환

- 새 안내와 댓글은 `hey`, `/hey`, `@hey`를 사용한다. 기존 `/reviewbot`·`@reviewbot`도 계속 처리한다.
- base의 `.hey.yaml`을 우선 읽고, 없으면 `.codereviewbot.yaml`을 읽는다.
- 기존 댓글 재사용과 답변 이력 연결을 위해 HTML 식별자, 과거 지적 ID와 `codereviewbot/questions` 상태 검사 이름을 유지한다. 보호 규칙을 바꿀 필요가 없다.
- Compose 프로젝트 이름(`codereviewbot`), DB 이름·사용자(`reviewbot`), n8n 워크플로·자격 증명 ID는 기존 볼륨과 설정을 재사용하도록 유지한다. 새 이미지 이름은 `hey-controller:0.1.0`, `hey-runner:0.1.0`이다.
- 실행 중인 배포와 실제 GitHub/GitLab 봇 계정, 저장소 주소, 터널·DNS는 별도 운영 설정이다. `botLogin`에는 실제 댓글 작성 계정을 유지하고, 연결 가이드의 `hey.example.com`은 소유한 도메인으로 바꾼다.

## Mattermost 알림

GitLab 저장소 설정의 `mattermostWebhookEnv: MATTERMOST_WEBHOOK_URL`로 알림을 켠다.
`.env`의 해당 변수에는 기존 채널의 Incoming Webhook URL을 넣는다. URL 전체가
비밀 값이므로 저장소·로그에 남기지 않는다. `mattermostChannel`로 채널을 지정할 수 있다.

- 첫 줄은 이름과 핵심 동작을 굵게 강조하고, 둘째 줄은 굵은 대상 링크로 표시한다.
  MR 대상은 `MR !번호 · MR 제목`이며 브랜치 이동 방향과 질문 개수는 표시하지 않는다.
- Push는 `**이름**님의 **커밋 N개**가 올라왔어요. 🚀`와 브랜치 비교 링크 다음에
  커밋 제목을 오래된 시각부터 한 줄씩 나열한다. 시간과 해시는 화면에 표시하지 않는다.
  각 제목은 해당 커밋으로 연결하며 `*feat:* **변경 내용**`처럼 유형은 기울임,
  내용은 굵게 표시한다. 일반 커밋 제목은 전체를 굵게 표시한다. 본문은 생략한다.
  웹훅에 전체 커밋이 없으면 [GitLab 비교 API](https://docs.gitlab.com/api/repositories/#compare-branches-tags-or-commits)로 보완한다.
  조회 실패 시 전송 전에 재시도하며 불완전한 목록을 보내지 않는다.
- 새 브랜치는 before SHA가 모두 0인 이벤트로 구분한다.
  `**이름**님의 **새 브랜치가 생겼어요.** 🌱`와 브랜치 커밋 목록 링크만 보낸다.
  브랜치 삭제·태그는 알리지 않는다. GitLab의 기존 hey 웹훅에서 Push events를 켠다.
  기본 MM Push 알림은 중복으로 켜지 않는다.
- MR 열기 📬, 다시 열기 🔄, 머지 🎉, 닫기 🗃️, 질문 준비 🧩, 댓글 💬로
  이벤트별 이모지를 구분한다. 이름은 성·소속을 제외하며 영문 이름은 첫 단어를 사용한다.
  MR·질문은 실제 MR 작성자, 댓글은 댓글 작성자, Push는 푸시한 사람의 표시 이름을 쓴다.
- 질문 게시가 끝나면 `**이름**님의 MR에 **질문이 준비됐어요.** 🧩`로 알리고
  대상 링크는 게시된 질문 댓글로 연결한다. 질문 수와 부분 분석·제외 범위는 GitLab에만 남긴다.
  동일 변경 범위는 한 번만 알리며 진행·실패·질문 없는 결과·채점 갱신·봇 답글은 전송하지 않는다.
- 사람 댓글은 대상 링크를 해당 댓글로 연결하고, 빈 줄 다음에 첫 줄을 `*“미리보기”*`로 표시한다.
  미리보기는 최대 200자이며 초과 시 말줄임표를 붙인다. 멘션·Markdown은 이스케이프하고
  알려진 인증 정보는 마스킹한다. 이전 큐 데이터에 미리보기가 없으면 두 줄로 표시한다.
- 수신 인증·저장소 허용 목록을 통과한 이벤트만 큐에 저장한다. 웹훅 URL은
  서버 설정에서만 읽고 전송 중에는 리다이렉트를 허용하지 않는다.
- n8n의 기존 tick이 알림 큐도 구동한다. 명시적 429 거절은 최대 3회 시도하고,
  응답 유실·재시작으로 전송 여부가 불명확하면 `uncertain`으로 남겨 자동 중복을 막는다.
  `mattermost_delivery` 로그와 `mattermost_notifications` 테이블에서 상태를 확인한다.

연결 검증 후 GitLab 기본 Mattermost 연동의 MR·Comment 알림만 끈다. 사람 댓글도
새 경로가 처리하며, Pipeline·Deployment 설정은 유지한다. 기존 댓글의 내부 태그는
GitLab에서 질문·답변 이력 연결에 계속 사용하되 MM 본문에는 포함하지 않는다.

발신자 `hey`는 웹훅의 `username`으로 요청한다. MM 서버의
`EnablePostUsernameOverride`가 `false`이면 기존 웹훅 소유자의 이름으로 표시된다.
현재 SSAFY 서버에서는 이 제한을 확인했으며, 시스템 관리자가 이름 덮어쓰기를
허용해야 한다. 사용자의 개인 프로필이나 새 봇 계정으로 대신 변경하지 않는다.

## 확인 명령

```sh
docker compose ps
docker compose logs --tail=50 controller runner n8n
curl --fail http://localhost:18092/healthz
```

`/internal/health`는 `.env`의 INTERNAL_TOKEN에 대한 Bearer 인증이 필요하다. 작업 수·실패 수·현재 실행 여부를 제공한다.
로그에는 작업 ID·단계·분류된 실패 원인만 남긴다. 모델 원문 대화나 Git 자격 증명을 출력하지 않는다.
실패 로그의 `cause`는 봇이 만든 오류 문구다. 구조화 출력이 계약과 다르면 `schema mismatch:` 뒤에 필드 경로와 오류 코드만 남긴다. 이 원인이 반복되면 컨트롤러와 실행기 이미지가 같은 소스에서 빌드됐는지 먼저 확인한다.

실제 모델 검증에서는 OAuth 인증 저장소의 사본을 운영과 독립적으로 계속 갱신하지 않는다. 같은 계정의 요청은 인증 상태가 갈라지지 않도록 직렬화한다. 사본을 사용했다면 운영 복귀 전에 원본을 백업하고, CLI `claude auth status`로 계정·조직 일치를 확인한 뒤 최신 인증 상태를 동기화한다. 로그인 상태 표시만으로 검증을 끝내지 않고 실제 모델 요청까지 확인하며, 인증 파일의 토큰은 출력하지 않는다.

## 중복과 장애

- 외부 이벤트를 DB에 기록한 뒤 응답한다. GitHub는 실패한 전송을 항상 자동 재전송하지 않으므로 1분 복구 조회도 사용한다.
- 전역 작업 lease로 한 번에 하나를 실행하며 15초마다 갱신한다. 90초 동안 갱신하지 못하면 재선점할 수 있다.
- 선점 토큰이 바뀌면 이전 프로세스의 결과 저장·게시를 거부한다.
- 댓글 쓰기는 무작정 자동 재전송하지 않는다. 60초 후 실제 플랫폼의 봇 소유 마커를 대조해 다음 시도를 한다.
- 단계별 최대 3회 시도 후 실패로 남긴다. 모델 사용량 제한·인증 오류는 즉시
  실패 사유를 게시하며, 실패 안내 게시를 성공한 질문 생성으로 집계하지 않는다.
  사용량 제한은 15분, 일시 연결·시간 초과 등은 5분 후 자동 복구를 최대 3회
  시도한다. 인증·출력 형식 오류는 자동 복구하지 않는다. 실패 댓글에는 다음
  재시도 시각(한국 시간)을 표시하며, 횟수 소진 시에는 자동 재시도를 약속하지 않는다.
  설정 복구 후 `/hey tryagain` 또는 인증된 `/internal/retry`에 작업 ID를 전달한다.
  생성 실패의 수동 재시도는 실제 질문을 다시 생성하고, 게시만 실패한 결과는
  저장된 질문을 다시 게시한다. 과거 실패 이력은 이후 성공해도 보존한다.
- 플랫폼 쓰기 직전 SHA를 확인하지만 원격 푸시와 쓰기를 원자적으로 잠글 수는 없다. 모든 질문은 출제에 사용한 커밋·diff 버전에 연결한다.
- 질문 요약·진행 안내·채점 갱신은 head/base/start 버전 마커로 같은 버전의 댓글만 수정한다. 새 푸시는 새 댓글을 만들며, 이전 버전과 버전 마커 없는 옛 댓글은 보존한다. 현재 코드의 옛 댓글은 저장된 질문 ID가 모두 일치할 때만 채점 갱신 시 연결한다. 게시 응답 유실 후 재시도는 같은 버전 마커를 대조해 중복을 막는다.
- 증분 출제에는 직전 출제 커밋 대비 실제 diff를 별도로 제공한다. 이 diff의 변경 전 줄은 직전 커밋 기준이며, MR/PR 인라인 좌표와 읽기 도구의 base는 MR/PR 기준 커밋이므로 구분한다. 마지막 출제 이후 변경을 묻되 최소 한 문항은 코드로 설명 가능한 목적·선택 이유를 다룬다. 코드로 확인할 출제 근거가 없으면 사유를 표시한다.
- 학습 질문·채점은 `jobs.command_result`에 최종 댓글과 질문을 저장한 후 게시한다. 게시 응답이 유실되면 같은 결과를 재사용하고 플랫폼의 봇 소유 마커를 먼저 확인한다.
- 댓글 식별은 GitHub 일반/리뷰 댓글과 GitLab note 영역을 포함한다. 업데이트 전 대기 중이던 이벤트는 이전 마커를 유지한다.
- 같은 head/base/start의 이전 질문은 작업 결과에서 복원한다. 같은 코드의 `/hey tryagain` 실패나 보고서 교체가 질문 ID를 무효화하지 않는다.
- 추가 질문 생성은 코드 버전별 PR/MR 전체에서 최대 5회다. 게시 대기·실패 후 재시도를 기다리는 저장 결과도 횟수에 포함한다.
- 학습 모델 입력은 500,000자 미만으로 유지한다. 필요하면 정책·코드 발췌를 줄이고 전체 코드는 읽기 도구로 확인한다. 질문 이력과 답변 자체가 너무 크면 생성·채점을 보류하는 안내를 남긴다.
- 일반 질문·심화 질문·채점·잘못된 명령 댓글에는 명령어 표나 반복 사용 예시 대신 도움말 한 줄을 표시한다. `/hey help`는 전체 6개 명령의 뜻·설명·사용 예시 표를 모델 호출 없이 반환한다. 질문이 없어도 동작한다.

## 질문 전용 버전으로 업데이트

1. 기존 DB와 인증 볼륨을 백업한다. DB를 초기화하거나 기존 작업·질문·답변 이력을 삭제하지 않는다. `jobs.command_result`의 멱등 마이그레이션도 유지한다.
2. 컨트롤러·실행기를 같은 소스에서 함께 재빌드한다. 초기 출제의 `initial_questions` 계약이 양쪽에서 일치해야 한다. n8n dispatch·recovery 연결 방식은 그대로다.
3. 새 결과는 `schemaVersion: "2"`로 저장한다. 이전 버전 결과는 같은 head/base/start SHA라도 최신 코드로 한 번 재생성한다. 전환이 끝난 결과는 같은 코드에서 재사용한다.
4. 이전 버전의 게시 대기 결과는 질문 생성 작업으로 돌린다. 옛 지적을 새 인라인 댓글로 게시하지 않는다. 원격에 이미 게시된 과거 댓글과 저장된 질문·답변 이력은 유지한다.
5. 이전 CI 대기 작업은 검사 결과 조회나 모델 호출 없이 종료한다. 새 CI 이벤트와 복구 조회는 CI 보고서 갱신 작업을 만들지 않는다. 선택적 `codereviewbot/questions` 답변 완료 상태는 계속 동기화한다.

초기 출제는 `initial_questions` 모델 호출 1회, 제한 120,000ms다. 출제 가능한 텍스트 근거가 없으면 0회다. 이 제한은 전체 처리 시간 보장이 아니며, 큐 대기·코드 준비·게시·실패 재시도는 별도다. 심화 출제(`questions`)는 한 번에 5개, 이유가 있는 답변의 채점(`grade`)도 호출당 120,000ms다. 보기 문자만 있는 답변은 저장된 정답키로 모델 없이 채점한다.

진행 댓글은 `질문 생성 중`·출제 범위·기준 커밋·예상 시간을 보여주고 최종 질문으로 바뀐다. 예상 시간은 `schemaVersion: "2"`인 질문 생성 이력의 중앙값을 사용하고, 이력이 없으면 측정되지 않은 기본값 2분을 표시한다. 과거 리뷰 시간은 사용하지 않는다. 운영 로그의 `questions_generated`는 `prepareMs`·`generateMs`·`modelCalls`, `questions_published`는 `publishMs`를 남긴다. 실제 모델의 정답 품질과 이전 방식 대비 시간 감소는 같은 변경 사례로 별도 측정한다.

## 데이터와 백업

`database`에는 작업·보고서·피드백과 별도 n8n DB가 있고, `codex-auth`·`claude-auth`에는 봇 전용 모델 인증이 있다.
`.env`, n8n encryption key, DB dump, 모델 전용 인증과 터널 자격 증명을 각각 보호해 백업한다.
원문 Git 캐시는 컨트롤러 전용 볼륨이며 실행기에 공유하지 않는다. 소스 스냅샷은 7일 후 복구 작업에서 정리한다.
작업·중복 방지·피드백 메타데이터는 자동 삭제하지 않는다. 운영 용량을 관찰하고 명시적 보존 정책을 정한 뒤 정리한다.

## Mac mini

Colima와 프로젝트를 다른 스택과 분리해 운영한다. 서버로 사용할 때는 로그인 후 Colima와 `docker compose up -d`를 실행하도록 macOS 로그인 항목/launchd를 설정한다.
필요하면 `caffeinate -s`로 전원 연결 중 시스템 잠자기를 방지한다. 이 구현은 시스템 전체 절전·로그인 설정을 자동 변경하지 않는다.
Mac이 꺼져 있거나 네트워크가 끊겼다면 복구 후 최신 열린 PR/MR부터 재동기화한다. 중간 푸시를 모두 재생하지 않는다.

Colima VM의 디스크는 Mac 호스트의 여유 공간과 별개다. `colima ssh -- df -h /var/lib/containerd`로 확인한다.
이미지 빌드와 PostgreSQL 초기화 전에 충분한 공간을 확보한다. 빌드 시 8 GiB 이상 여유를 권장한다.
공간 부족 오류가 나면 이 프로젝트를 정지하고, 소유가 확인된 이전 이미지·빌드 캐시만 정리한다.
다른 프로젝트를 포함하는 전역 prune이나 볼륨 삭제는 복구 명령으로 사용하지 않는다.

## 현재 한계와 검증 범위

- 질문은 고정 코드 스냅샷의 정적 읽기를 근거로 생성한다. 코드 품질과 테스트 결과 확인은 작성자의 작업이며 봇은 CI 결과를 수집·보고하지 않는다.
- 구조·중복·코드 위치·정답키 형태는 프로그램이 검사한다. 정답의 의미적 정확성을 보장하는 2차 모델 검토는 없다. 실제 변경 사례에서 잘못된 전제·정답 오류·학습 가치·소요 시간을 평가해야 한다.
- SDK/CLI 버전은 고정한다. 업데이트 때 MCP 도구 목록, 셸 비활성화, `initial_questions`·`questions`·`grade` 구조화 출력과 실패 처리 테스트를 재실행한다.
- 전용 GitHub App/토큰의 인스턴스별 권한, 실제 GitLab 버전의 signing 지원, 질문 스레드·도움말 렌더링과 머지 조건은 실연동 단계에서 확인한다.
- 민감 파일 제외와 알려진 자격 증명 마스킹은 방어 수단이며 모든 형태의 하드코딩된 비밀을 탐지하는 보장은 아니다.
- 로컬 fixture와 HTTP·PostgreSQL 테스트는 제어 흐름을 검증한다. 실제 모델 품질이나 운영 환경의 시간 단축을 검증한 것으로 간주하지 않는다.

## 명령 정리 버전으로 업데이트

- 재생성은 `/hey tryagain`으로 요청한다. 도움말에는 답변·정답 보기·심화 질문·재생성·코드 질문·도움말 6개만 표시한다.
- 시작 시 마이그레이션이 사용하지 않는 `targets.paused` 컬럼과 `feedback` 테이블을 제거한다. 기존 일시정지 대상의 대기 작업은 다시 처리되며 질문·답변·보고서 이력은 유지한다.
- 저장소 규칙은 기준 브랜치의 `.hey.yaml`, `AGENTS.md`, `docs/coding-standards.md`에서 관리한다.

### GitLab 봇 계정 교체

새 프로젝트 토큰은 기존과 같은 Developer 역할, `api`·`read_repository` 범위와 만료일로 발급한다. `botLogin`은 새 토큰의 `/user` 응답에 나온 username으로 바꾸고, 예전 username은 `retiredBotLogins`에 남긴다. 이 목록은 봇의 명령·MM 알림을 걸러내기 위한 설정이며, 예전 댓글을 수정할 권한을 부여하지 않는다.

기존 토큰을 해제하기 전에 해당 프로젝트의 MR별 notes/discussions를 인증된 API로 읽고, 예전 봇이 작성한 hey 마커 댓글을 `Store.rememberBotComments`로 등록한다. `bot_comment_history`의 MR·댓글 종류·원격 ID가 일치하는 댓글만 과거 봇 댓글로 인정한다. 일반 사용자가 마커를 복사한 댓글은 인정하지 않는다. GitLab이 만료·해제된 봇의 작성자를 ghost로 바꿔도 등록된 질문 스레드는 계속 인식한다.

질문 ID와 `targets.report`, `jobs.result`, `jobs.command_result`는 변경하지 않는다. 새 봇은 자기 요약 댓글을 작성·갱신하며 예전 댓글을 수정하거나 삭제하지 않는다. 요약에는 저장된 채점이 반영되고, 등록된 인라인 질문은 중복 게시하지 않는다. 프로젝트별 이력과 댓글 본문을 전후 비교하고 새 봇의 실제 명령 응답을 확인한 뒤 기존 토큰을 해제한다. 해제 후에는 기존 토큰을 되살릴 수 없으므로 코드 롤백에도 새 토큰을 유지한다.

### MM 알림이 갑자기 멈춘 경우

MM 전송 오류와 GitLab 수신 중단을 먼저 구분한다. 해당 프로젝트의 `mattermost_notifications` 마지막 성공 시각·대기 상태와 GitLab Webhook Recent events 응답을 함께 확인한다. DB 접속이 `57P03`(recovery mode)로 실패하면 Colima 디스크의 여유 공간과 PostgreSQL의 `No space left on device` 오류를 확인한다. 컨트롤러 재시작만 반복하거나 DB/WAL 파일을 삭제하지 않는다. 데이터·인증 볼륨과 운영·직전 복구 이미지를 보존하고 공간을 확보한 다음 PostgreSQL 연결 수락, 컨트롤러 health, n8n tick 순서로 확인한다.

공개 `/healthz`는 터널 경로 설정에 따라 404일 수 있다. 로컬 `/healthz` 200, 공개 `/webhooks/gitlab`의 인증 없는 POST 401, GitLab에서 재전송한 실제 요청 202와 MM 채널의 실제 메시지를 복구 기준으로 삼는다. 장애 중 요청은 DB 알림 큐에 들어오지 못했을 수 있으므로 큐가 비었다고 누락이 없다고 판단하지 않는다. 최신 열린 MR은 recover로 재동기화하고, 과거 이벤트를 전부 무차별 재전송하지 않는다.

### 5주 운영을 위한 저장량 제한

- 질문·답변·채점·중복 처리 이력과 DB·인증 볼륨은 운영 기간 내내 보존한다. Git 캐시는 재사용한다.
- 원본 코드의 임시 작업 복사본은 6시간만 보관한다. 기존 recover가 정리하며, DB 작업 claim과 같은 잠금으로 대기·실행·게시 중인 작업을 보호한다. 심볼릭 링크는 정리 대상에서 제외한다.
- 모든 서비스 로그는 Docker `local` 드라이버로 압축·순환 저장한다. 서비스당 5MB 파일 2개, 합계 약 50MB의 로그 분량을 한도로 한다(메타데이터 제외).
- n8n 성공·수동·진행 실행 데이터는 저장하지 않는다. 오류 실행은 48시간·최대 500건으로 제한한다. 실행 이력 정리는 n8n의 기존 기능이 담당하며 워크플로·자격 증명은 보존한다.
- 빌드 전에 `node scripts/storage.mjs --check-build`로 Mac과 Colima에 각각 8GiB 이상 여유가 있는지 확인한다. 운영만 할 때는 새 이미지나 빌드 캐시를 만들지 않는다. 의존성 변경 없는 검증된 코드 교체는 현재 이미지 위에 dist만 복사하는 작은 이미지를 사용한다.
- 배포 확인 후 `node scripts/storage.mjs --apply --keep-image <직전-복구용-이미지>`로 불필요한 hey 이미지를 정리한다. 실행·정지 상태를 포함한 모든 컨테이너의 참조 이미지와 명시한 복구 이미지는 보존하고, 볼륨·다른 프로젝트 태그·전역 빌드 캐시는 삭제하지 않는다. 옵션 없는 실행은 정리 계획만 출력한다.
- PostgreSQL 통합 테스트는 테스트 컨테이너를 제거할 때 그 컨테이너의 익명 볼륨도 함께 제거한다. 운영 볼륨에는 적용하지 않는다.
