# hey의 Mac → edo1 마이그레이션 기록과 운영 절차

작성일: 2026-10-25, 시간대: Asia/Seoul. 대상 독자는 hey 운영자와 이후 서버 이전을 담당할 개발자다.

## 1. 결과와 적용 범위

Mac의 Colima에서 실행하던 hey를 SSH 별칭 `edo1`의 새 Docker Compose 프로젝트 `hey-edo1`로 이전했다. 애플리케이션 기능을 변경하지 않고 실제 배포 중이던 버전 `252d5c85b55dc8127ba8eacf390b1f316c1e4116`을 보존했다. 작업 시작 시 체크아웃된 저장소의 HEAD는 `706c9c4`였으므로, 체크아웃 소스를 그대로 배포하면 실행 버전이 과거로 돌아갈 수 있었다.

| 항목 | 이전 전 | 이전 후 |
|---|---|---|
| 실행 위치 | Mac의 Colima VM | edo1, `/home/ubuntu/hey` |
| CPU | Linux ARM64, `aarch64` | Linux AMD64, `x86_64` |
| Compose 프로젝트 | `codereviewbot` | `hey-edo1` |
| 컨테이너 | controller, runner, postgres, n8n, tunnel | 동일한 역할의 새 컨테이너 5개 |
| 질문 생성 제공자 | GMS | 기존 GMS 설정 유지 |
| GitLab 웹훅 | `https://codereviewbot.thisis-joe.com/webhooks/gitlab` | 동일 주소 유지 |
| DB 이름 | `reviewbot`, `n8n` | 동일 이름 유지 |

이전 전 Docker 데이터 디스크는 40GB가 모두 사용된 상태였다. PostgreSQL이 비정상 상태였고 컨트롤러가 재시작을 반복했다. 따라서 이 작업은 정상 서비스의 무중단 이전이 아니라, 디스크 장애가 발생한 원본에서 데이터를 복구한 뒤 실행 위치를 바꾸는 작업이었다. 무중단 이전이나 장애 기간 전체의 이벤트 복구를 주장하지 않는다.

최초 점검에서 edo1은 루트 디스크 약 269GB, 사용 가능한 메모리 약 12GB를 확보하고 있었다. 기존 edo1의 웹 서비스, Jenkins, MySQL, Grafana, Metabase는 변경하지 않았다.

## 2. 무엇을 이전했는가

### 애플리케이션과 연결 설정

- 실행 컨테이너의 환경 변수, 시작 명령, 서비스 간 주소와 인증 토큰.
- 실제 배포 이미지의 JavaScript 모듈 31개, DB 마이그레이션 파일과 패키지 목록.
- 저장소 허용 목록, GitLab 봇 로그인, 웹훅 인증 방식과 Mattermost 연결 설정.
- 기존 Cloudflare Tunnel 토큰. DNS와 공개 웹훅 주소는 유지했다.
- 읽기 전용 파일 시스템, 권한 제한, 메모리 제한, 내부망 분리, localhost 포트 바인딩 등 기존 실행 구성을 바탕으로 한 서버 설정.

### 데이터와 파일

| 원본 볼륨 | 용도 | 이전 방법 |
|---|---|---|
| `codereviewbot_database` | hey와 n8n의 PostgreSQL 데이터 | 원본 파일 백업 → 별도 ARM 복사본에서 복구 → SQL 덤프 → 새 AMD64 클러스터에 복원 |
| `codereviewbot_snapshots` | 질문 생성용 작업 스냅샷 | 정지 상태의 파일 백업과 복원 |
| `codereviewbot_git-cache` | Git 저장소 캐시 | 파일 백업과 복원 |
| `codereviewbot_codex-auth` | Codex 인증·상태·캐시 | 파일 백업과 복원, CPU별 임시 실행 파일은 재생성 |
| `codereviewbot_claude-auth` | Claude 인증·상태 | 파일 백업과 복원 |

새 볼륨 이름은 `hey-edo1_database`처럼 `hey-edo1_` 접두사를 사용한다. n8n의 워크플로 ID `crbDispatch`, `crbRecovery`와 자격 증명 ID를 보존했다. `N8N_ENCRYPTION_KEY`도 유지하여 저장된 자격 증명을 다시 복호화할 수 있게 했다.

## 3. 실제 진행 순서

### 1단계: 원본과 목적지 조사

먼저 저장소의 Compose 파일과 배포 기록을 읽고, 실제 컨테이너의 이미지 ID·리비전·환경 변수·볼륨·네트워크·상태를 조사했다. 비밀 값은 일반 로그나 이 문서에 출력하지 않았다. 실제 설정 원본은 접근을 제한한 작업 파일로만 보관했다.

SSH 연결에는 `ClearAllForwardings=yes`를 적용했다. `edo1` 별칭에 이미 설정된 로컬 포트 전달이 기존 연결과 충돌했기 때문이다. 파일 전송과 원격 명령 실행에는 포트 전달이 필요하지 않았다.

목적지에 기존 hey 프로젝트가 없는 것을 확인한 뒤 `/home/ubuntu/hey`를 권한 `700`으로 생성했다. 새 프로젝트와 네트워크 이름을 사용해 기존 서버 서비스와 충돌하지 않도록 했다.

### 2단계: 원본 정지와 일관된 백업

원본 tunnel, n8n, controller, runner, postgres를 정지해 복사 중 쓰기를 막았다. 이후 실제 프로세스와 컨테이너 상태도 확인했다. 디스크가 가득 찬 상태에서는 Docker의 상태 표시 갱신도 늦거나 실패할 수 있으므로, 명령의 성공 문자열만으로 정지를 판정하지 않았다.

정지된 6개 볼륨을 `volumes-offline.tar.gz`로 백업했다. 원본 DB 데이터는 약 127MB였다. 파일의 내용뿐 아니라 소유자·그룹·권한·심볼릭 링크도 복원에 필요한 정보로 취급했다.

원본 컨테이너와 볼륨은 목적지 검증이 끝날 때까지 유지했다. 기존 서비스와 새 서비스가 동시에 웹훅을 처리하지 않도록 원본 터널을 먼저 정지했다.

### 3단계: 공간 부족을 우회한 DB 복구

Docker 디스크가 가득 차 일반적인 `docker cp`, 로그 읽기, 새 컨테이너 시작에 제약이 있었다. 다른 프로젝트의 로그나 볼륨을 지우는 대신 다음과 같이 원본과 분리된 복구 공간을 사용했다.

1. Colima 루트 디스크의 `/tmp`에는 약 16GB의 여유 공간이 있음을 확인했다.
2. 원본 PostgreSQL 데이터 디렉터리를 `/tmp/hey-recovery-20261025/pgdata`로 복사했다.
3. hey의 재생성 가능한 Codex 임시 플러그인 캐시 약 103MB를 같은 임시 공간으로 이동했다. DB 원본을 축소하거나 WAL 파일을 삭제하지 않았다.
4. containerd의 기존 PostgreSQL ARM 이미지 파일 시스템을 임시 경로에 연결했다.
5. 복사된 데이터와 임시 소켓·장치 경로를 연결하고, 기존 ARM PostgreSQL 17.11을 별도 프로세스로 실행했다.
6. 원본과 분리된 복사본에서 WAL 재생과 복구 체크포인트가 완료되고, 연결을 수락하는 상태가 됨을 확인했다.

이 복구 프로세스는 Docker 컨테이너를 추가 생성하는 대신 기존 이미지의 프로그램을 분리된 루트 경로에서 실행한 임시 환경이었다. 포트는 Colima 내부의 `127.0.0.1:55432`를 사용했다. 복구 중 변경된 것은 복사본이며 원본 DB 볼륨은 그대로 두었다.

로그에는 이전 비정상 종료와 복구 중단 이력이 나타났다. 이를 정상 상태로 간주하지 않고, 이후 전체 SQL 덤프와 `pg_amcheck --heapallindexed` 검사까지 수행했다. 두 DB의 테이블·인덱스 검사 명령은 성공했다. 검사에 필요한 `amcheck` 확장은 덤프 생성 이후 임시 복사본에만 설치했다.

### 4단계: SQL 백업과 비교 기준 생성

복구된 ARM PostgreSQL에서 `pg_dumpall`로 역할과 데이터베이스를 포함한 전체 SQL 덤프를 만들었다. CPU가 다른 서버 사이에서 데이터 디렉터리를 그대로 운영하지 않고 SQL로 다시 적재하기 위한 조치였다. PostgreSQL은 다른 아키텍처로의 이전에 SQL 덤프를 사용하는 방법을 설명한다. [PostgreSQL 백업 문서](https://www.postgresql.org/docs/17/backup-dump.html)

복원 비교를 위해 각 사용자 테이블의 행 수와 내용 해시를 기록했다. 테이블마다 각 행의 JSON 표현을 해시하고, 행 해시를 정렬하여 테이블 해시를 구했다. 비교할 때 양쪽 세션의 시간대를 UTC로 통일했다. `timestamptz` 값은 같은 시각이어도 세션 시간대에 따라 JSON 문자열이 달라질 수 있기 때문이다.

첫 비교에서 시간대 표현 때문에 해시가 달랐으며, UTC로 통일한 후 모든 테이블이 일치했다. 행 수만 같은 것으로 데이터 보존을 판정하지 않았다. 이 해시는 이전 전후 내용 비교용이며 백업의 암호화 수단은 아니다.

### 5단계: AMD64 이미지 구성

ARM 이미지를 edo1에 그대로 실행하지 않고 AMD64 이미지를 생성했다. 질문 생성 로직은 실제 배포 이미지에서 추출한 31개 모듈을 사용했다. 로컬 체크아웃이나 기본 이미지 태그가 최신 배포를 대표한다고 가정하지 않았다.

서버용 이미지 이름은 다음과 같다.

```text
hey-controller:edo1-252d5c8
hey-runner:edo1-252d5c8
```

Node.js 22.23.2 기반에서 고정된 패키지 목록으로 의존성을 설치했다. 애플리케이션 패키지와 Codex 설치에는 자동 설치 스크립트를 끄는 옵션을 사용했다. Claude Code 2.1.290은 기존 설치 스크립트를 읽어 플랫폼별 바이너리를 배치하는 동작을 확인했고, 파일 해시가 같은 스크립트만 명시적으로 실행했다.

원본 코드 파일 일부는 제한된 읽기 권한을 가지고 있었다. 새 이미지에 root 소유로 복사한 상태에서는 `node` 계정이 읽지 못해 runner 시작이 실패했다. `/app`의 코드와 의존성을 읽을 수 있도록 이미지 권한을 수정한 뒤 재빌드했다. 컨테이너를 root로 실행하는 방식으로 우회하지 않았다.

### 6단계: 새 PostgreSQL 초기화와 SQL 복원

새 PostgreSQL 17.11 클러스터를 초기화했다. 이때 기존 초기화 스크립트가 `reviewbot`, `n8n` 역할과 DB를 먼저 생성하면 전체 덤프와 충돌하므로, 초기 복원용 Compose 설정에서는 해당 바인드 마운트를 제외했다.

SQL 복원에서는 새 클러스터에 이미 존재하는 `CREATE ROLE postgres;` 문장만 제외했다. 덤프의 `ALTER ROLE`과 나머지 역할·DB·데이터 정의는 유지했다. `psql`에 `ON_ERROR_STOP=1`을 설정하여 복원 오류가 발생하면 진행을 중단하도록 했다.

복원이 끝난 뒤 원래 초기화 스크립트 마운트를 포함하는 최종 Compose 설정으로 PostgreSQL을 재생성했다. 기존 데이터 볼륨이 초기화되어 있으므로 초기 생성 스크립트가 다시 실행되어 데이터를 덮어쓰는 방식은 아니다.

이어서 나머지 5개 파일 볼륨을 복원하고, 원본 아카이브의 UID·GID·권한을 디렉터리까지 적용했다. 특히 `--strip-components`로 경로를 제거하면서 복원하면 볼륨 최상위 디렉터리의 원래 소유권이 적용되지 않을 수 있었다. n8n이 `crash.journal`에 쓰지 못한 문제는 최상위 디렉터리 메타데이터를 복구해 해결했다. Git 캐시와 작업 디렉터리에는 실제 파일 생성·삭제 검사도 수행했다.

### 7단계: 데이터와 실행 버전 검증

컨트롤러·runner를 먼저 시작하고 다음을 확인했다.

- reviewbot의 5개 테이블, n8n의 157개 테이블에서 행 수와 내용 해시 일치.
- controller와 runner 각각의 JavaScript 모듈 31개 해시 일치.
- 핵심 서비스의 설정된 환경 변수 값이 원본 실행 환경과 일치.
- PostgreSQL, controller, runner의 healthcheck 성공.
- Codex CLI `0.163.0`, Claude Code `2.1.290`의 실제 실행 성공.
- 기존 인증·상태·캐시 파일의 내용 비교 성공. Codex가 실행 중 자동 정리하는 `tmp` 실행 보조 파일은 비교에서 제외했다.

파일 비교는 Codex 상태 5,499개, Claude 상태 382개, Git 캐시 1,536개, n8n 상태 6개 파일·링크를 대상으로 성공했다. 스냅샷 볼륨은 보존할 파일이 없는 상태였으며, 쓰기 권한은 별도로 검사했다. 파일 내용 비교와 UID·GID·권한 복원은 별개의 검사로 수행했다.

### 8단계: 실제 질문 생성과 공개 주소 전환

새 controller의 실제 모듈에서 runner RPC와 기존 GMS 설정을 거쳐 질문 2개를 생성했다. 기존 검증에 사용한 과거 코드 변경 사례를 입력으로 사용했으며, 생성에는 약 39.051초가 걸렸다. 문항 개수와 형식 검증이 통과했다.

이 검증은 외부 PR/MR에 댓글을 게시하지 않았고, 운영 질문·작업 기록을 생성하지 않았다. 임시 입력 스냅샷은 실행 후 삭제했다. 한 사례의 성공으로 모든 저장소의 품질·응답 시간이나 동시 부하를 검증했다고 해석하면 안 된다.

그다음 n8n과 tunnel을 edo1에서 시작했다. 기존 Tunnel 토큰을 사용했으므로 GitLab 웹훅 URL과 DNS 변경 없이 연결 위치가 바뀌었다. 터널 로그에서 한국 리전의 연결 4개와 기존 ingress 규칙 수신을 확인했다.

공개 경로는 `^/webhooks/(github|gitlab)$`만 controller로 전달한다. 따라서 공개 주소의 `/healthz`가 404를 반환하는 것은 기존 ingress 정책에 따른 정상 결과다. 내부 localhost의 `/healthz`는 200, 인증 없는 공개 GitLab 웹훅은 401을 반환했다.

### 9단계: 자동화와 외부 접근 검증

n8n의 상태 확인 외에도 실제 wake 웹훅 호출의 202 응답, GitLab 프로젝트 API 접근의 200 응답을 확인했다. n8n의 `crbDispatch`, `crbRecovery` 활성화와 새 실행 기록의 만료 표시도 확인했다.

기존 정책은 성공 실행 본문을 보관하지 않고 실행 기록을 즉시 삭제 대상으로 만든다. DB의 `status=running` 문자열만 보면 실행이 멈춘 것으로 오해할 수 있어 `deletedAt`도 함께 확인했다. 검증 시 새 실행 중 `deletedAt IS NULL`인 기록은 0개였다. 기존 정책을 바꾸지 않았다.

GitLab 봇 토큰으로 웹훅 관리 목록을 읽는 API는 403을 반환했다. 웹훅 주소는 과거 배포 검증 기록과 터널이 수신한 ingress 설정으로 확인했다. 프로젝트 접근과 공개 웹훅 라우팅은 별도로 통과했다.

### 10단계: 백업 보관과 Mac 정리

edo1에서 전환 후 SQL 덤프를 추가 생성하고 백업 압축 파일을 검사한 뒤 Mac 자원을 정리했다. 원본 5개 컨테이너의 자동 재시작을 먼저 껐으며, 이후 사용자 요청에 따라 원본 컨테이너와 볼륨을 삭제했다.

정리 완료 항목과 남겨 둔 범위는 아래의 Mac 정리 기록 및 검증 JSON을 따른다. 원본을 삭제한 이후에는 단순히 Mac 컨테이너를 다시 켜는 롤백을 할 수 없다. 보관된 SQL·파일 백업으로 복구 환경을 새로 구성해야 한다.

## 4. 보존 결과와 판단 기준

| hey 테이블 | 이전 전·복원 후 행 수 |
|---|---:|
| `targets` | 38 |
| `jobs` | 146 |
| `deliveries` | 186 |
| `mattermost_notifications` | 180 |
| `bot_comment_history` | 38 |

기존 작업 상태는 completed 113건, failed 20건, superseded 13건이었다. 알림은 sent 179건, uncertain 1건이었다. 이를 일괄 재시도하거나 삭제하지 않았다. 특히 uncertain은 전송 성공 여부가 불명확하므로 재전송하면 중복 알림이 발생할 수 있다.

최종 내부 상태는 `failed=10`, `queued=0`, `active=false`였다. 여기서 failed는 단순한 `jobs.state='failed'`의 개수가 아니다. 대상의 실패 보고서와 별도의 작업 실패를 합산하는 기존 상태 API의 집계이므로 테이블의 failed 20건과 구분한다. 기존 실패 기록을 이전 성공 여부와 혼동하지 않았다.

## 5. 목적지의 운영 방법

### 상태 확인

아래 명령은 실제 배포에서 사용한 경로와 Compose 파일을 기준으로 한다. `compose.json`은 비밀 값이 포함된 운영 설정이므로 전체 출력을 공개 로그에 붙여 넣지 않는다.

```sh
ssh -o ClearAllForwardings=yes edo1
cd /home/ubuntu/hey
docker compose -f compose.json --profile tunnel ps
curl -fsS http://127.0.0.1:18092/healthz
curl -fsS http://127.0.0.1:5688/healthz
docker compose -f compose.json logs --tail 50 controller runner
```

controller는 `127.0.0.1:18092`, n8n은 `127.0.0.1:5688`에만 공개한다. PostgreSQL과 runner는 호스트 포트를 열지 않는다. n8n 관리 화면이 필요하면 SSH로 별도 로컬 포트를 전달한다. 이는 배포 중 확인한 포트 구성에 근거한 접속 예시이며, 아래 포트 전달 명령 자체는 이번 검증에서 실행하지 않았다.

```sh
ssh -o ClearAllForwardings=yes -L 15688:127.0.0.1:5688 edo1
```

연결 후 브라우저에서 `http://127.0.0.1:15688`에 접속한다.

### 재시작

```sh
cd /home/ubuntu/hey
docker compose -f compose.json --profile tunnel up -d --no-build
```

최종 서비스의 재시작 정책은 `unless-stopped`다. 서버 재부팅 자체는 이번 작업에서 시험하지 않았다. 운영 중에는 수동 stop 이후 자동 기동되지 않는 경우와 Docker 서비스 자체의 기동 상태도 구분해야 한다.

### 백업 위치와 접근 제한

| edo1 파일 | 의미 |
|---|---|
| `backups/cluster.sql.gz` | 원본 ARM 복구본에서 생성한 전체 SQL 덤프 |
| `backups/volumes-offline.tar.gz` | 원본 정지 상태의 6개 볼륨 파일 백업 |
| `backups/post-cutover.sql.gz` | edo1 전환 후 SQL 덤프 |
| `backups/migration-evidence-20261025.tar.gz` | 이번 이전의 설정 원본·실행 코드·검증 파일·원본 ARM DB 이미지 백업 |
| `backups/retired-mac-monitor.tar.gz` | 종료한 Mac 디스크 알림 등록 정보 |
| `evidence/` | 최종 실행 상태 등의 운영 증거 |

파일 경로는 모두 `/home/ubuntu/hey` 기준이다. 배포 디렉터리는 `700`, 운영 Compose 설정과 백업 파일은 `600`으로 확인했다. SQL 덤프에는 인증 관련 정보가, 파일 백업에는 코드·인증 상태가 포함될 수 있다. Git 저장소, 공개 문서나 일반 채팅에 첨부하지 않는다.

이 백업은 edo1의 동일 디스크에 있다. 목적지 디스크나 계정 자체를 잃는 장애까지 대비한 외부 백업은 별도 과제다. 이번 작업에서 주기적 백업 자동화나 백업 보관 기간은 새로 설정하지 않았다.

## 6. 장애 시 복구 원칙

다음 절차는 보관된 산출물과 실제 복원에 사용한 방법에 근거한 운영 계획이다. 서비스 전환을 되돌리는 전체 리허설은 수행하지 않았다.

1. 공개 수신을 담당하는 tunnel과 작업을 깨우는 n8n부터 정지해 추가 처리를 막는다.
2. 가능한 경우 장애 시점의 DB와 파일을 별도 이름으로 백업한다. 정상 백업 파일을 덮어쓰지 않는다.
3. 백업의 압축 무결성과 SHA-256을 확인하고, 별도의 새 프로젝트·볼륨에서 복원을 시작한다.
4. 같은 PostgreSQL 메이저 버전의 빈 클러스터에 SQL 덤프를 복원한다. 초기화 스크립트의 중복 역할·DB 생성과 기존 postgres 역할 충돌을 처리한다.
5. 파일 볼륨의 내용과 최상위 디렉터리를 포함한 UID·GID·권한을 복원한다.
6. 모듈 해시, DB 테이블 행 수·내용 해시, 내부 상태, GMS 질문 생성, n8n 호출을 확인한다.
7. 기존 실행이 완전히 정지한 것을 확인한 뒤 한 곳에서만 tunnel을 활성화한다.

애플리케이션 이미지만 교체해도 DB가 과거로 돌아가지는 않는다. 반대로 전환 전 SQL 백업으로 DB를 되돌리면, 백업 이후 생성된 질문·답변·웹훅 수신 기록을 잃을 수 있다. 데이터 손실 범위는 복구에 선택한 백업 시점에 달려 있다. 이미 게시된 GitLab 댓글과 Mattermost 메시지는 DB 복원으로 사라지지 않으므로 중복 처리와 재전송을 별도로 대조해야 한다.

Mac으로 돌아가는 경우에도 삭제한 로컬 볼륨을 다시 만들고 데이터를 복원해야 한다. 원본 Mac의 공유 Docker 디스크 문제도 먼저 해결해야 한다. 따라서 원본 삭제 이후의 복구 목표를 단순한 컨테이너 재시작 시간으로 약속하지 않는다.

## 7. 주의한 점과 남은 한계

- **실제 실행 버전 확인:** 체크아웃 HEAD와 운영 버전이 달랐다. 배포 이미지의 리비전과 실제 파일을 우선했다.
- **아키텍처 차이:** 앱 이미지는 AMD64로 만들고 DB는 ARM에서 복구 후 SQL로 옮겼다. ARM 전용 임시 CLI 심볼릭 링크는 새 서버에서 재생성되는 항목으로 구분했다.
- **원본 보존:** 원본 DB에서 WAL 삭제, 강제 초기화, 테이블 삭제를 수행하지 않았다. 원본 제거는 목적지 검증과 백업 후 별도 사용자 요청에 따라 실행했다.
- **소유권 보존:** 파일 해시 일치만으로 정상 실행을 판단하지 않았다. 코드 읽기 권한, 볼륨 루트의 쓰기 권한과 실제 쓰기를 검사했다.
- **중복 방지:** 원본 터널을 끄고 새 터널을 켰다. uncertain 알림과 실패 기록을 일괄 재시도하지 않았다.
- **비밀 정보:** 토큰을 문서에 기록하지 않고, 설정·백업 접근을 제한했다. 인증서를 새로 발급하거나 토큰을 회전시키지는 않았다.
- **네트워크 격리:** 내부 통신망과 localhost 관리 포트를 유지했다. GitLab에는 기존 웹훅 주소를 그대로 사용했다.
- **범위 제한:** 다른 프로젝트의 컨테이너·로그·DB를 삭제하지 않았다. 전체 Docker 시스템 정리 명령을 사용하지 않았다.
- **이전 중 유실 가능성:** 기존 장애 시간에 공급자가 보낸 모든 이벤트가 나중에 재전송되었는지까지 감사하지 않았다. 실패한 GitLab 웹훅 전송 기록의 대조와 필요한 이벤트의 선별 재전송은 별도 운영 작업이다.
- **외부 게시 범위:** 실제 GMS 생성과 GitLab 읽기 접근은 검증했지만 새 MR 댓글이나 Mattermost 테스트 메시지는 게시하지 않았다.
- **n8n 경고:** Python 3 부재와 내부 task runner의 향후 변경 경고가 있었다. 사용 중인 HTTP 기반 관리 워크플로와 JavaScript runner의 동작은 확인했으며 Python 실행 환경을 추가하지 않았다.
- **장기 운영 범위:** 부하 시험, 서버 재부팅 시험, 전체 롤백 리허설, edo1 전용 디스크 알림·외부 백업 자동화는 수행하지 않았다.

## 8. Mac 정리 기록

실행 자원 정리는 이전 검증과 edo1 백업 보관이 끝난 후 수행했다.

- 원본 컨테이너 5개 정지, 자동 재시작 해제 후 삭제.
- hey 전용 데이터 볼륨 6개 삭제.
- `hey-controller`, `hey-runner`, `codereviewbot-controller`, `codereviewbot-runner` 저장소에 속한 이미지 태그 52개 제거.
- 사용 중인 컨테이너가 없는 원본 Compose 네트워크 7개 제거.
- 임시 ARM PostgreSQL 복구 프로세스 종료와 이미지·디렉터리 연결 해제.
- Mac의 `com.thisisjoe.hey.disk-monitor` launchd 작업 해제와 등록 파일 제거. 이 알림 작업을 edo1에 새로 설치하지는 않았다.
- 로컬 운영 `.env`, 실제 저장소 연결 설정, 빈 GitHub 비밀 파일, 이번 이전의 백업·작업 디렉터리, 종료한 모니터 설정과 과거 루트 테스트 로그 등 53개 경로 삭제. 추적 중인 소스와 설정 예제는 유지했다.
- Colima의 임시 복구 데이터·이미지 연결 경로·캐시 복사본 삭제. 정리 후 Docker 디스크 여유 공간은 약 6.1GiB로 확인했다.

추가 임시 파일 삭제 및 최종 잔여 자원 검사는 [검증 기록](verification/hey-edo1-migration-2026-10-25.json)의 `macCleanup`을 따른다.

과거 작업 자료를 포함하는 `.local` 전체를 서버로 복사하려는 작업은 자동 승인 검토에서 관련 없는 자료·비밀 정보 혼입 가능성으로 거부되었다. 이후 이번 마이그레이션에서 생성한 명확한 범위의 증거만 보관했다. 이전 채팅의 `.local` 자료와 `consistent-copy` Git worktree 등 개발 이력은 보존한다. 공유 Colima, 다른 서비스가 사용하는 기반 이미지, 소유권을 입증할 수 없는 익명 볼륨도 삭제하지 않는다.

이 정리는 hey의 로컬 실행 자원을 제거한 것이다. 다른 프로젝트가 함께 사용하는 Mac Docker 디스크 전체의 용량 문제를 해결했다고 의미하지 않는다.

## 9. 검증 자료

일반 공유 가능한 수치와 결과는 [검증 JSON](verification/hey-edo1-migration-2026-10-25.json)에 기록했다. 비밀 값과 생성 질문 원문을 포함할 수 있는 세부 자료는 edo1의 비공개 증거 백업에 있다.

이번 변경은 기능별 브랜치 `codex/migrate-hey-edo1`에서 수행했다. 저장소 변경은 운영 문서와 검증 기록이며, 애플리케이션 소스 변경에 대한 단위 테스트 통과를 새로 주장하지 않는다. 실제 목적지 이미지 빌드·DB 복원·파일 대조·HTTP·RPC·GMS·자동화 실행 검증을 이전의 완료 기준으로 사용했다.
